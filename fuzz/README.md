# Fuzzing

`config` feeds bytes to `Config::parse`. A config that parses is validated with the shadow check on, serialized back to JSON, parsed again, and must give the same number of validation errors. Needs nightly Rust, so run it in Docker from the repo root:

```
docker run --rm -v "$PWD":/w -v veilway-fuzz-target:/w/fuzz/target -v veilway-fuzz-cargo:/usr/local/cargo -w /w rustlang/rust:nightly sh -c "cargo install cargo-fuzz --locked; mkdir -p /tmp/corpus; cargo fuzz run config /tmp/corpus fuzz/corpus/config -- -max_total_time=300 -dict=fuzz/dict/config.dict -max_len=65536"
```

`packet` feeds bytes to the header parser every decrypted packet goes through (`engine::netstack::parse`), to the same parser as it reads the packet an ICMP error quotes (`engine::netstack::quoted`), and to the answers the node writes itself: the TCP reset, the echo reply and the ICMP errors of every kind (`engine::icmp::error`). A packet that parses must have its upper-layer header inside it, an echo reply must parse and go back to the sender, and an ICMP error must parse, go from the gateway to the sender, quote exactly the start of the packet it answers within the size the RFCs allow, and never be answered with another error. It needs no seeds or dictionary: replace `config` with `packet` in the command above and drop the `fuzz/corpus/config` and `-dict` arguments.

`dns` feeds bytes to the two readers of the node's resolver (`engine::dns::query` and `engine::dns::response`), which see every DNS message from a tunnel and from an upstream server. A query that is read must give REFUSED and SERVFAIL answers that read back as answers to it. Replace `config` with `dns` in the command above, drop the `-dict` argument and use `-max_len=4096`.

`state` feeds bytes to the two things the control channel added to the engine that read what the node did not write. With an even first byte the rest is a usage state file (`engine::usage::parse`), which since the control channel also holds the exit each device chose: every count that is read must be one a file can hold, and every exit must be a tag. With an odd first byte the rest is a packet that is cut to fit a device's MTU (`engine::netstack::fragments` and `forward`): every fragment must fit, be a fragment, and together they must carry what the packet carried. A packet that fits must not be cut at all, and no more users and devices are kept of a file than a node writes. Without its seeds the target never finds a whole packet and only the state file half runs: they are in `fuzz/corpus/state`, written by `crates/veilway-core/tests/seeds.py`, and `tests/seeds.rs` of that crate fails when one no longer reads. Replace `config` with `state` in the command above, use `fuzz/corpus/state`, drop the `-dict` argument and use `-max_len=4096`.

`chunk`, `control_stream`, `fuzz_control_server` and `fuzz_control_client` feed bytes to the wire formats in `veilway-proto`. The first bytes of an input are settings, described at the head of each target, and the rest is what is fed. None of them stops at a cryptographic check: the harness seals the plaintext or runs the real other side of the exchange, so the code behind the check sees fuzzed input. All four have seeds, written by `crates/veilway-proto/tests/vectors.py`, and a test in that crate (`tests/seeds.rs`) fails when a seed no longer reads.

- `chunk`: a chunk plaintext that the harness seals and the opener must then read exactly as the reading rules say, a sealed chunk from the wire, items to seal, or a plaintext for the reader and writer alone. A sealer must refuse exactly the items a reader would refuse, and an opener that failed must stay failed. Use `fuzz/corpus/chunk`, no dictionary and `-max_len=20000`.
- `control_stream`: the byte stream of a control channel connection after its opening, in either direction, cut into pieces. It must read the same in pieces as whole, an error must be final, every message that reads must be written back as the same bytes, and a catalog that is handed out must keep its rules. Use `fuzz/corpus/control_stream`, `-dict=fuzz/dict/control.dict` and `-max_len=20000`.
- `fuzz_control_server`: the node's side of the control channel. A real client runs the exchange while the input picks the secret, one byte to change on the way, the pieces and the time of each call, and the node must open exactly when the secret is right, nothing was changed and the deadline was kept. The rest of the input is then read as requests. With bit 0 of the first byte set, the input goes to a node as it is, and the node must take at most 80 bytes and never open. Use `fuzz/corpus/fuzz_control_server`, `-dict=fuzz/dict/control.dict` and `-max_len=4096`.
- `fuzz_control_client`: the same for the client's side, against a real node or an impostor that has no key. The rest of the input is then read as the node's messages, and what a client would show must stay inside its bounds. Use `fuzz/corpus/fuzz_control_client`, `-dict=fuzz/dict/control.dict` and `-max_len=20000`.

`stream_proof`, `udp_obfs`, `replay_file`, `request_line` and `fronted_body` feed bytes to the transports' wire formats in `veilway-proto`, in the same shape: settings first, and a harness that gets past the cryptographic check. A real client makes the token or the packet, or seals a hello or an opening packet that no client would (`Client::forge`, which exists only in a fuzzing build), and the target knows in advance whether the node must accept it. Their seeds come from `vectors.py` too. All five take `-dict=fuzz/dict/transports.dict`.

- `stream_proof`: the node's side of the stream proof. The input picks the device's secret, the node's transport keys, the transport on each side and one character to change, and the node must open the token exactly when it has the secret and the key, the transports are equal and nothing was changed. A sealed hello must be accepted exactly when its version, zero bytes, tag, binder and padding are the ones the specification allows, and never with an epoch tag in the place of the device tag. A token that opens goes to the replay rule, which must accept it once and give the keys the client has. A text from a stranger must never open. Every one of these costs a client's two scalar multiplications and the node's, so one mode leaves the client out: the input is changes to one real token that is made once, and the node must open it exactly when nothing is left changed. Use `fuzz/corpus/stream_proof` and `-max_len=512`.
- `udp_obfs`: the opening packet and the data packet. The same for an opening packet, with the client's epoch up to two away from the node's and one table for both kinds of tag, then the replay rule, then a data packet each way under the session's keys. A data packet sealed here around any plaintext must open exactly as a chunk of one datagram or none reads. Use `fuzz/corpus/udp_obfs` and `-max_len=4096`.
- `replay_file`: the replay file as found on disk, the same with a right hash added so the reader decides by the rules behind the hash, and the replay rule under a sequence of proofs, clock steps of seconds and of a day, the node's timer, stops, starts that are killed, crashes, lost files and resets. Every write the node is asked for ends as the input says: written, lost, or reported failed and on disk all the same. No proof may be accepted twice or above a limit that is not on disk, and in the other direction the floor may never be more than the window and the step above the highest clock value seen since the last reset unless a proof that high was accepted, and a limit that only a wrong clock raised must come back down. Use `fuzz/corpus/replay_file` and `-max_len=4096`.
- `request_line`: what a stream listener reads before it knows who is there. The scanner must decide at the byte a second writing of the rule decides at, the same in pieces as byte by byte, and a complete line must split into its parts and back. Use `fuzz/corpus/request_line` and `-max_len=8192`.
- `fronted_body`: the body of a `fronted` request, sealed here around any plaintexts, with a chunk at a wrong number or a cut end if the input says so. The opener must accept it, end the session, or leave the session exactly as it was, as the specification says for each case. Use `fuzz/corpus/fronted_body` and `-max_len=70000`.

`fuzz_deeplink`, `fuzz_sub_envelope`, `fuzz_subscription`, `fuzz_links` and `fuzz_sub_request` feed bytes to the subscription format in `veilway-proto`. Their seeds come from `vectors.py` as well, and `tests/subscription.rs` of that crate fails when one of the documents, links or requests among them no longer reads. All five take `-dict=fuzz/dict/subscription.dict`, and a run of them uses its own volumes: replace `veilway-fuzz-target` with `veilway-fuzz-target-sub` in the command above.

- `fuzz_deeplink`: a link as it is typed, pasted, scanned or opened, and the content of a file. A link that reads must be written back as the bytes it was read from, a native link must read the same in both forms and never print its token, and a legacy link must come out of nothing but an `https` URL. What a link becomes is an offer, which holds no request. Use `fuzz/corpus/fuzz_deeplink` and `-max_len=4096`.
- `fuzz_sub_envelope`: the verifier of the envelope on bytes nobody signed, and on a good document with bytes changed. Nothing verifies but what a holder of a private key wrote in its one form, and a changed document never does. Use `fuzz/corpus/fuzz_sub_envelope` and `-max_len=4096`.
- `fuzz_subscription`: the payload reader behind a good signature. The harness signs the input as a payload with a fixed test key, so every byte of it reaches the reader, and then gives the document to a client: as the answer to a refresh, of a client that holds a whole document with a provider-issued key or of one that imported a link with a key its device made, or as a whole document to import. A payload that reads must be within every limit, a refresh that fails must leave what is held exactly as it was, and one that is taken must be of the same subscription, of a higher serial, not issued earlier and with no device key the client did not have. A request may go only to the endpoint of the link and to hosts the user confirmed, and nowhere for a whole document. The cards of a provider are read here, so the threat model's `fuzz_cards` is this target. Use `fuzz/corpus/fuzz_subscription` and `-max_len=16384`.
- `fuzz_links`: the body and the headers of the answer to a legacy `GET`. What is read must stay inside its limits, every field must be of its kind, and no entry may dial what a signed profile may not. The headers are the threat model's `fuzz_sub_headers`. Use `fuzz/corpus/fuzz_links` and `-max_len=16384`.
- `fuzz_sub_request`: the body of a request as an endpoint gets it. A body that reads must read back from the one body a client writes for it. Use `fuzz/corpus/fuzz_sub_request` and `-max_len=2048`.

`fuzz_pairing` feeds bytes to the two codes of node link pairing in `veilway-proto` (`pairing::Offer::parse` and `pairing::Answer::parse`), which a person pastes into a panel. The first byte picks what the rest is: the text of an offer or of an answer, or the object of an offer or the bytes of an answer, which the harness then puts into a code with a checksum that holds, so that the reader behind the checksum sees fuzzed input. A code that reads must be within every limit of the node links page and be written back as the text it was read from, and an offer that reads must pair: a dialler answers it, a listener that issued the same terms takes that answer, each side refuses its own value of the fingerprint and half of the other's, and takes the other's whole, and both hold one secret. Its seeds come from `vectors.py`, and a test of `pairing` fails when one of them no longer reads. Use `fuzz/corpus/fuzz_pairing`, `-dict=fuzz/dict/subscription.dict` and `-max_len=4096`.

The threat model also names `fuzz_card_logo` and a target for the Encrypted Client Hello configuration. Neither exists here: `veilway-proto` hands the logo and the configuration on as bytes, and their readers, an image decoder and the TLS library, are not in this crate.

`obfs_listener` feeds datagrams to the node's `udp-obfs` listener as a whole (`engine::obfs`), with everything behind it but the socket: the tag table, the replay rule, the limits per device and per source, the session table and the inbound's WireGuard. The node has three devices, one of them with two transport secrets, and the input is a list of steps from four sources: bytes from a stranger, opening packets of a device around any datagram or around a real handshake initiation, data packets of the sessions that were opened, around any datagram or around what the device's WireGuard sends next, any packet the harness sent before, answered or dropped, sent again from the same or another source, and steps of the node's clock with its timers, at which the limit a proof asked for is written and the opening packets that waited for it go to the replay rule again. The head of the target lists the settings of a step. Whatever the input is, the node must send nothing and take nothing out of the tunnel unless the packet holds an authentic WireGuard packet of the session's own device and has not been answered before, a first answer must be no larger than the opening packet of its session, a packet that was answered once must never be answered again from any source, a packet the node keeps for a higher limit must be answered at its own source or nowhere, and the node must hold no more pending sessions than two for each device and no more established ones than its pool has places. Its three seeds in `fuzz/corpus/obfs_listener` are written by hand, in printable bytes. Replace `config` with `obfs_listener` in the command above, use `fuzz/corpus/obfs_listener`, drop the `-dict` argument and use `-max_len=2048`.

`tls_listener` feeds bytes to the node's stream listener as a whole (`engine::stream`), with everything behind it but the socket and the TLS library: the request line test, the stream proof under the node's transport key, the tag table, the replay rule, the limits, the pools, the handoff to the decoy origin and the session that follows an accepted proof. Each input is one connection of a direct peer over a pipe in memory, written in pieces of a size the input picks, against a node with three devices and a stub origin that reads a connection to its end and answers once, or, when the input says so, answers before it reads anything, or closes at once. The input is a stranger's bytes as they are, the request line of a real and fresh proof with any bytes behind it, a real upgrade request with one thing about it that makes it no proof (a changed character, another path, another method, another transport's name, a timestamp outside the window, another HTTP version), or a good upgrade request followed by any bytes as the frames of its session, with a real handshake initiation in a real chunk first if the input says so. The head of the target lists the settings. Whatever the input is, a stream that is no accepted proof must reach the origin whole and unchanged, and its peer must get the origin's answer and not one byte besides. A stream that begins with a real proof of a device must be accepted, nothing of it may reach the origin, and its peer gets the upgrade answer, or nothing when the head is no upgrade. With an origin that answers or closes first, a real proof may also end as a stranger's stream, because such an origin can decide a connection before its request line is complete, and a stranger of an origin that closed at once gets nothing. The harness serves one connection to its end before the next, so displacement, a full pool, proofs that wait for a limit and the rate limits are not reached here: the tests of `crates/veilway-core/tests/tls.rs` have those. The node's listener over pipes is behind the `bench` feature of `veilway-core`, which only this crate and the tests turn on. When a connection is over the node must hold nothing of it: no undecided or relayed connection, no pending session and no session. One node serves the whole run, with a clock every input moves ahead, so the replay memory and the limits are those of a node that has run for a while. Its seeds in `fuzz/corpus/tls_listener` are written by hand, in printable bytes. Replace `config` with `tls_listener` in the command above, use `fuzz/corpus/tls_listener`, `-dict=fuzz/dict/transports.dict` and `-max_len=4096`, and its own volume for the build: replace `veilway-fuzz-target` with `veilway-fuzz-target-tls`.

`proxy_listener` and `fronted_session` feed the proxy path of the same listener (`engine::stream`), which the `ws` and `fronted` transports of a `veilway` inbound arrive by: a connection of a trusted proxy over a pipe in memory, read request by request. Both run the node on a runtime whose clock is paused and jumps to the next timer when nothing else can run, so a hold time of 250 ms, a head that never ends and five quiet minutes cost nothing, and a node that waits for ever fails the run instead of hanging it.

- `proxy_listener`: any bytes, in pieces of a size the input picks, with a real WebSocket open or a real opening request of a `fronted` session behind them if the input says so. The stub origin behind the node reads requests by a rule of its own, written in the target apart from the node's (`veilway_proto::http`), answers each request the moment it has all of it and keeps the connection, and from the first thing that is no request answers once with an error and only reads. What the origin receives must be the bytes the proxy sent, from the first on and in order, and what the proxy gets back must be what the origin wrote and nothing besides. While everything so far was a whole request, the origin must never hold a byte beyond the request it is about to answer: that is where a node that took a request to end elsewhere than the origin does would show, by handing on too much or by waiting with the rest in its hands. When the payload is whole requests and nothing else, the origin gets all of them and a user behind them is a user. What it does not reach: two connections at once, an origin that closes, resets or answers in pieces, and a head that takes more than its ten seconds, which `crates/veilway-core/tests/ws.rs` has. Use `fuzz/corpus/proxy_listener`, `-dict=fuzz/dict/http.dict` and `-max_len=20000`.
- `fronted_session`: one session for each input, opened with a real proof and a real WireGuard handshake, and then up to 24 requests of the kinds the input names: the client's next request, a repeat of the last one, the last number with other bytes, a number out of order, the next number with a body nobody sealed or with chunks that were sealed for numbers already used, and requests with a wrong method, path, session id or number. Every request of the client must be accepted in order with an answer the client can open, however many of the others stand between them, a repeat must get the stored answer byte for byte, and every other request must reach the origin whole with the origin's answer coming back. That is what "a session's state changes only on accepted requests" comes to: had anything else moved it, the client's next request would not open. What it does not reach: two requests at once, which `crates/veilway-core/tests/fronted.rs` has, and a chunk that opens and is invalid, which no key of a real proof can be made to seal from outside the crate and which the `fronted_body` target has at the level of the opener. Use `fuzz/corpus/fronted_session`, no dictionary and `-max_len=64`.

Their seeds are written by hand. Both use their own volume for the build: replace `veilway-fuzz-target` with `veilway-fuzz-target-b3`.

`client_upgrade`, `client_frames`, `client_fronted`, `client_udp` and `client_choice` feed bytes to what the client's side of the transports reads from the network (`crates/veilway-transport`): a node, a front and the path are all hostile to it. The first bytes of an input are settings, described at the head of each target, and where a reader stands behind a cryptographic check the harness is the node, with `veilway-proto`'s own sealers, so the code behind the check sees fuzzed input.

- `client_upgrade`: the head of the answer to an upgrade request (`http::head`, `Head::upgraded`, `http::date`), as it is or as field lines inside an answer that would open a session. A head must be found only where a second writing of the rules finds one, a session must open exactly for a `101` of HTTP/1.1 with one accept field of the right value, and a `Date` that is read must be written back as the same bytes. Use `fuzz/corpus/client_upgrade`, `-dict=fuzz/dict/http.dict` and `-max_len=20000`.
- `client_frames`: the frames of a `tls` or `ws` session (`stream::Reader`): bytes as they are, or chunks sealed here as the node seals them, with a ping in front of each or one bit changed if the input says so. The stream must read the same in pieces as whole, the reader must keep less than one frame when it asks for more and stay failed once it failed, and no datagram may come out that the node did not seal. Use `fuzz/corpus/client_frames`, no dictionary and `-max_len=20000`.
- `client_fronted`: the answer to a `fronted` request (`http::response`, then the body under the session's key): bytes as they are, or a body sealed here behind a head with its length, with one bit changed, the length named twice or a byte behind the body if the input says so. An answer must be found at its last byte and not before, a verdict must not turn back into an answer, and a body that opens must hold what the node sealed. Use `fuzz/corpus/client_fronted`, `-dict=fuzz/dict/http.dict` and `-max_len=20000`.
- `client_udp`: the client state machine of `udp-obfs` (`udp::Machine`) between a caller, a clock and what arrives from the node's address: datagrams nobody sealed, the node's answers under the keys of any of the client's opening packets, the same with one bit changed, steps of the clock, datagrams of the caller and changes of network. Every packet the client sends must be an opening packet of the device or a data packet of one of its sessions, none above the `mtu` and 62 bytes, and the client must take only what the node sealed and be established by nothing else. Use `fuzz/corpus/client_udp`, no dictionary and `-max_len=2048`.
- `client_choice`: the decisions of `choice` (which transport, which candidate, which wait) over a state nobody vouches for. The head of an input is a profile and a `Network` and a `Standing` as a damaged or stale state file would hold them, with places, counts and times of any value, and the rest is steps: candidates asked for, attempts that end in every way one can, a transport with nothing left, the clock moving on or back, the user asking to connect again or changing consent, and a refresh that changes the list of transports. No class below the best may be planned without the user's yes, and a transport must be planned whenever one is allowed. Nothing that is set aside may be given out while something else is free. On the last transport a candidate must come at once or after a wait that ends within the hour. After every call no mark may last beyond an hour from now, nothing in the state may lie in the future, and no wait may be longer than an hour. Use `fuzz/corpus/client_choice`, no dictionary and `-max_len=512`.

Their seeds are written by hand, in printable bytes. They use their own volume for the build: replace `veilway-fuzz-target` with `veilway-fuzz-target-tc`.

One check of `veilway-proto` is neither a fuzz target nor part of an ordinary test run: the timing of the stream proof's opener, which needs a release build and a quiet machine. Run it before a release and after any change to `crates/veilway-proto/src/proof.rs` or to the `hpke` dependency. Its head says what it can and cannot see:

```
docker run --rm -v "$PWD":/w -v veilway-target:/w/target -v veilway-cargo:/usr/local/cargo -w /w rust:1 cargo test -p veilway-proto --release --locked --test timing -- --ignored --nocapture
```

New inputs go to the first corpus directory (`/tmp/corpus`, lost with the container), so the tracked seeds in `fuzz/corpus/config/` stay as written. To keep a good new input, copy it into the seed directory by hand. A crash is saved under `fuzz/artifacts/config/`; shrink it with `cargo fuzz tmin config <file>`.
