# Veilway threat model

This document is binding. Protocol, panel and client code is reviewed against it, and a change that breaks an invariant in section 7 is a bug even if every test passes. It was first written before any of the new design existed. The core engine of `PLAN.md` Phase 1 is now built up to live reload (config v1, several inbounds, routing rules, the `netstack` and `l3` exits, the node's resolver), and the parts about it describe code. The native protocol, the panel and the multi-platform client do not exist yet, so the rest still describes requirements, not results.

## At a glance

A one-page summary. The sections below are the reference, and where they differ from this page they win.

**Who uses it.** People on censored or hostile networks who reach the internet through a node that someone they trust runs. The provider (the node and panel operator) is trusted with their traffic; the network in between is not.

**What we protect, in order** (section 3):
1. That a person or an address uses Veilway at all (AS1), and that a node stays reachable (AS2). On a censored network this comes before everything else.
2. What goes through the tunnel and who it goes to, from anyone on the path (AS3, AS4).
3. The keys: device keys, node and transport keys, the provider's signing and gateway keys, subscription links (AS5, AS6).
4. The panel, the node host, the client device, and the release and update keys (AS7, AS9 to AS11).
5. Users of one node from each other (AS12).

**Who we defend against** (section 5): a censor that inspects traffic and actively probes servers; a provider who turns malicious; hostile subscriptions, theme files and links; a stolen panel session; a hostile peer inside the tunnel or a hostile upstream proxy; another provider whose subscription the node uses as an exit, which sees what that exit carries and is held to U1 to U9 in section 5.15; anyone who reaches a proxy inbound, held to P1 to P10 in section 5.16; a third party's Xray server that carries an exit, held to X1 to X8 in section 5.17; a third party's WireGuard server that carries an exit, held to W1 to W7 in section 5.20; an attacker on the update path or the local network; the supply chain; the hosts of mirrors and the Xray add-on.

**The rules that hold whatever the config says** (section 7, binding, each with a test):
- A listener says nothing to a stranger that the decoy site would not say, and a stranger cannot tell a user's path from a refusal by bytes or timing.
- A proof is accepted once, also across a restart.
- No cryptography is written here; only reviewed libraries.
- Transport keys are separate from WireGuard keys, per device where they can be, and revocable.
- Every packet from a device is checked for its own source address before anything else, and the always-refused destinations are refused before any rule.
- Everything read from the network, a subscription, a theme or a provider is treated as hostile and fails closed (section 6 lists every parser).

**What we do not promise** (section 9): beating an observer who sees both ends; protection when a device, node or panel is itself compromised; anonymity from the provider; that a user cannot be recognized across sessions; that any transport is undetectable (only that named probes did not detect it on a given date); stopping abuse of an exit; security of the Xray protocols beyond the upstream software; surviving a large denial-of-service attack or a seized unlocked device; isolation between users that the operator's own rules turn off.

**Where to look next.** What is not finished: section 8. Questions still open in the protocol: section 10. How this document stays true: section 11.

## 1. How to read this

**Status labels.** Every mechanism carries one of four labels.

| Label | Meaning |
|---|---|
| Built | Exists in the current code. If a test covers it, the test is named. If no test covers it, the text says "read from code, not tested". |
| Partial | Exists but is known to be incomplete. The gap is listed in section 8. |
| Not built | Required by this document, absent from the code, and either absent from `PLAN.md` or contradicted by a dependency's default. Listed in section 8 where current code is affected. |
| Planned | Described in `PLAN.md`, not written yet. Nothing planned is a security property until it is built and its test in this document passes. |

**What "tested" means here.** The test suite has 194 test functions (`cargo test --workspace`). They were counted in the source for this revision, which was made by reading code and tests and not by a new run. They cover the WireGuard endpoint wrapper, the WebSocket relay and its limits, config v1 (parser, validation, reload store), the engine end to end on loopback (ingress checks, the destination gate, routing rules, the flow table, the node's resolver, ICMP errors, the `unsupported` policies, live reload and cut-off) and the client engine. Three of them drive the `l3` exit against a real kernel. Those run only with `VEILWAY_TEST_L3=1` in a container that has `CAP_NET_ADMIN`, as the header of `crates/veilway-core/tests/l3.rs` says, and are not part of the CI run. There are three fuzz targets (`config`, `packet`, `dns`, section 6), run by hand and not in CI. There are no probe-resistance measurements, no traffic-analysis measurements and no external review. The tunnel cryptography is WireGuard as implemented by boringtun and is not re-verified by this project.

**Code references** name a function or a test, not a line number, and place it in the crate from the `PLAN.md` repository layout (`veilway-wg`, `veilway-core`, `veilway-client`, `apps/desktop`). Search for the symbol if a path has moved.

**Addresses** in examples come from RFC 5737 (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`) and `example.com`.

## 2. System summary

Built today: a core that runs one JSON config (version 1) with several inbounds. Each inbound is one WireGuard tunnel in userspace (boringtun) with its own key and address pool, reachable over UDP or over WebSocket (one WireGuard datagram per binary frame). Users have devices, and a device is a public key with fixed tunnel addresses. Every decrypted inner packet passes a source check and a fixed destination gate. Routing rules then decide per flow: an exit, delivery to another device inside the node, or refusal, and a bounded flow table keeps the decision. An exit has one of three backends: `netstack` (a userspace TCP/IP stack that re-dials each flow through a SOCKS5 proxy or directly from the node, with no TUN device, no kernel routing and no privilege), `l3` (Linux only: one TUN device, kernel forwarding and source NAT, `CAP_NET_ADMIN`) and `block`. The node answers tunnel DNS itself and remembers names per user for `domain` rules. The config is reloaded on `SIGHUP`, and a user who is disabled, removed or expired is cut off while connected. A Windows desktop client drives a Wintun adapter, routes and DNS policy.

One thing is different from the first version of this document and matters everywhere below: isolation between users and access to private networks are no longer fixed properties of the server. Routing rules decide both. Section 5.6 states what is still enforced whatever the rules say and what is now the operator's responsibility.

Built since: quotas with usage kept in a state file, and the control API on a unix socket (`veilway-api`). Built since as well: the node's side of the control channel on `veilway` inbounds (`engine/control.rs`, over the wire formats of `veilway-proto`), which carry the `udp` and `udp-obfs` transports. Built since as well: the node's side of `udp-obfs` (`engine/obfs.rs`) and the replay memory with its file that every obfuscated transport will share (`engine/replay.rs`), both over the wire formats and the replay rule of `veilway-proto`. No client speaks `udp-obfs` yet, and neither part has been reviewed. Built since as well: the node's side of `tls` and the stream listener for a direct peer (`engine/stream.rs`), with the limits per device and per source that every native transport is held to together (`engine/limits.rs`). No client speaks `tls` yet, the listener has not been reviewed, and `tls` is rated Detectable whatever its tests show. Built since as well: the proxy path of that listener and, on it, the node's side of the native `ws` and of `fronted` (`engine/stream.rs`, with `veilway_proto::http` for where a request and its answer end). No client speaks either, neither has been reviewed, neither has been run behind a real web server or a real CDN, and both are rated Detectable (G53 to G55). Not built in the core yet: remote access to the control API, the client's side of the control channel and of every transport, GeoIP beyond the name `geoip:private`, and the `chain` exit.

Planned (`PLAN.md` "Core design", "The native protocol", "Transports"): the `veilway` inbound (WireGuard tunnel, pluggable transport, control channel inside the tunnel), transports `udp-obfs`, `tls`, `faketls`, `fronted` and later `quic`, the `chain` exit, GeoIP and geosite rules, quotas, a control API, a web panel, signed subscriptions with provider cards and themes, the optional Xray sidecar, and clients for Windows, macOS, Linux and Android.

## 3. Assets

| Id | Asset | Why it matters |
|---|---|---|
| AS1 | Fact of use: that a given network address runs or uses Veilway | On a censored network this is the first thing an adversary wants, and it is enough to block a node or single out a user. |
| AS2 | Reachability of a node: its addresses, names and fronts staying unblocked | A blocked node is a lost node for every user on it. |
| AS3 | Tunnel content: inner IP packets | Confidentiality and integrity between client and node. |
| AS4 | Tunnel metadata: destinations, DNS names, volume, timing, client address | Visible to the node by design, must not be visible to the path. |
| AS5 | Long-term keys: user WireGuard private keys, node static keys, preshared keys, transport authentication secrets | Impersonation and, for transport secrets, retrospective detection. |
| AS6 | Provider signing key (Ed25519), the gateway key of the subscription endpoint (X25519), and subscription URLs | Whoever holds the signing key can reconfigure every subscribed client. Whoever holds the gateway key and recordings of subscription requests reads them, tokens included. A subscription URL is a bearer secret. |
| AS7 | Panel credentials, sessions, TOTP seeds, database, audit log | Full control of users, nodes and exits. |
| AS8 | Upstream credentials (SOCKS5, chained nodes) | Abuse of someone else's proxy, and traffic interception. |
| AS9 | Client host integrity: routes, DNS policy, the privileged process, local files | The client changes system networking with administrator rights. |
| AS10 | Node host integrity and resources | Other users of the node, and anything else on that machine. |
| AS11 | Release signing keys, updater key, add-on hash list, CI | Whoever controls these controls every installation. |
| AS12 | Isolation between users of one node | One user must not see, reach or degrade another. |

| Boundary | Crossing | Trust rule |
|---|---|---|
| B1 | Webview to client engine | The webview is less trusted than the engine. The engine validates every command argument. Provider strings reach the webview only as text. |
| B2 | Engine to OS configuration | Only typed values (addresses, prefixes, integers) and constants reach a command line or system API. |
| B3 | Client to path | Everything on the path is hostile. The path sees transport bytes only. |
| B4 | Path to transport listener | All input is unauthenticated until WireGuard, or the transport's own proof, accepts it. No identifying answer before that. |
| B5 | Tunnel to engine | The peer is authenticated and still hostile (section 5.6). |
| B6 | Exit to upstream | The upstream is semi-trusted for delivery and untrusted for content, replies and addresses it returns. The DNS servers the node's resolver asks through an exit are untrusted in the same way. |
| B7 | Browser to panel server | An authenticated session is not proof of intent. State changes need a CSRF token, sensitive ones need recent re-authentication. |
| B8 | Panel to core | The core authorizes every call by token scope or socket ownership. It does not trust the panel database. |
| B9 | Core to sidecar | The sidecar is a separate OS process with a generated config, reachable on loopback only. Its stats output is untrusted input. |
| B10 | Provider to client | Provider content is authenticated data from a party that may be malicious (section 5.2). |
| B11 | Files to any parser | Attacker-controlled bytes. Section 6 lists every parser. |
| B12 | Download hosts to installer | Transport security is not relied on. Signature or pinned hash decides. |
| B13 | `l3` exit to host kernel | The kernel forwards what the engine writes to the interface. Whatever the host routes into the interface is untrusted input and is delivered only as the answer to a live flow. The node changes host state only with typed values and fixed argument lists (section 5.11). |
| B14 | Config document to core | The core validates every document itself, at start and on every reload, and keeps the running config whole when one is refused. A valid document is trusted completely: it decides isolation, exits, entitlement and what is logged. Today it comes from a file, later also from the control API. |

## 5. Adversaries

Each subsection lists the assets at stake, the adversary's capabilities, what the design does with the mechanism that provides it, what is not defended, and how the defense is tested.

### 5.1 Censor with DPI and active probing

**Assets:** AS1, AS2, AS4.

**Capabilities:** observes every packet between client and node, including sizes, timing and direction; keeps flow records for later analysis; injects, drops, delays and resets packets; connects to any address and port it has seen and sends anything (active probing); replays bytes captured from real clients; blocks by address, port, SNI, DNS answer, protocol signature or behavior; can obtain subscriptions and client binaries the same way a user does, so it knows the software, node public keys from leaked subscriptions and the front lists in them; may hold a CA that client operating systems trust; may throttle everything it cannot classify, or allow only what it can.

| Technique | Design response | Mechanism | Status |
|---|---|---|---|
| Passive protocol fingerprint of plain WireGuard (message type byte 1 to 4, three reserved zero bytes, sizes 148, 92, 64 and 32 + 16n) | Plain `udp` is rated Detectable and never presented as resistant. Obfuscated transports wrap every datagram. | "Security rating shown to users"; transports `udp-obfs`, `tls`, `ws`, `faketls`, `fronted` | Rating planned. `udp` and `ws` built. Others planned. |
| Length and timing fingerprint through TLS | Framing adds a length field and padding so WireGuard's sizes do not show through record lengths. | "The native protocol", layer 2 | Planned. The built `ws` transport maps one datagram to one frame with no padding (G14). |
| Active probing of a TCP listener | Anything that is not a valid client is handed to the decoy origin: the operator's own web server, with no third-party decoy in version 1. To a prober the node answers with the decoy's bytes and close behavior, except that on `tls` the TLS handshake is the node's own (invariant 1). Timing cannot be identical: a splice or reverse proxy adds the hop from node to origin, and invariant 3 bounds and publishes that residual. For `faketls` (designed, not built, section 5.14) a stranger is relayed byte for byte to the borrowed site and sees its own handshake and certificate, except that a copy of a user's hello gets a flight the node makes with the sizes and times the site showed for those same bytes. | "Rules for building it", first rule; Phase 2 step 3. `engine/stream.rs`: `conn` (the accept state machine of a direct peer), `prove` (steps 1 to 7 of the proof), `relay` (the handoff) | Built on the node for `tls`, for a direct peer. **Not defended:**

- A censor that blocks everything it cannot classify, or allows only a list of addresses. If no front in the list is reachable, Veilway does not work there.
- Address blocking of a node that has no CDN or front. Changing the address is the only remedy.
- Statistical traffic analysis: flow correlation, website fingerprinting from sizes and timing, volume profiling. Padding raises the cost and proves nothing.
- A censor holding any valid subscription. It knows every address, key and front in it, can confirm each node by connecting as a client, and for a transport whose secret is node-wide can passively recognize every user of that node and pass the proof when probing (invariant 5b).
- A censor that blocks a whole CDN.
- Fingerprints going stale. A browser-matching ClientHello is correct for one browser release. Section 9 covers this.
- Throttling or packet loss that makes stream transports unusable.
- `faketls`: a censor that checks whether the destination address belongs to the SNI's published addresses or ASN, and a censor that compares TCP-handshake round-trip time with TLS-handshake round-trip time to detect a relay hop.
- CDN-terminated transports (`fronted`, `ws` behind a CDN): the CDN sees the inner framing and the client's address, and so does anyone the CDN answers to.
- The encapsulated TLS handshake fingerprint, at v1.
- Residual timing of WireGuard's handshake and keepalive timers after padding and jitter. The measurement in the testing list bounds it and does not remove it.
- Enumeration of `tls` node names through Certificate Transparency logs, which publish every ACME-issued certificate, and a node name that hosts nothing but a decoy.

### 5.2 Malicious provider

A provider runs a panel and nodes and hands subscriptions to users. Users choose a provider. A provider is not trusted with the user's device.

**Assets:** AS9, AS5 (the user's keys for other providers), the integrity of the client UI, and the user's traffic while not connected to that provider.

**Capabilities:** signs any subscription content with its own key; controls every node the profile points at, so it sends arbitrary control channel messages, arbitrary inner IP packets towards the client, and arbitrary DNS answers; chooses names, notices, cards, links, logos, exit catalog, update interval and transport hints; can serve different content to different users; sees the address and timing of every subscription refresh.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| Code execution or markup injection through content | Provider content is data. Cards are a closed set of four types, plain text, no HTML, no markdown, no remote images, at most 6, capped strings. | "Provider cards" | Planned |
| Hostile logo image | One embedded raster under 64 KB, decoded and re-encoded by the client before display, with dimension limits. | "Provider cards" | Planned |
| Phishing through links | `https` only, the domain is shown, opening needs a confirmation. | "Provider cards" | Planned |
| Passing itself off as the application | Provider content is visibly separated from the app's own UI and can be hidden. One accent color, clamped for contrast, built-in icons only. | "Provider cards" | Planned |
| Lying about how safe a profile is | The rating is computed by the core from the effective settings. No profile, subscription or control channel field can set it. A disabled certificate check rates Unsafe. | "Security rating shown to users" | Planned. Today a profile can set `InsecureTls` with no warning (G9). |
| Hostile control channel values (addresses, DNS, MTU, hints, notices) | The client validates every value against bounds and never lets a server message weaken the kill switch, DNS pinning or rating (invariant 23). | Control channel spec | Planned. The spec lists every value a client takes and its bound (Q6) |
| Command injection into the privileged client | Only typed values reach `netsh`, `route` and PowerShell. | `win::open` in `veilway-client` takes `IpAddr`, `IpNet`, `u16` and a constant adapter name | Built, read from code, not fuzzed |
| Silent takeover of another provider's subscription | A subscription is identified by its signing key and its signed subscription id together. **Not defended:**

- The provider reads and can modify everything the user sends through its nodes that is not protected end to end by the application (TLS inside the tunnel is the user's protection). It sees destinations, DNS names, volume, timing and the client's address. Veilway is not an anonymity system against the provider.
- The provider answers DNS. It can lie.
- The provider can reach services on the client that listen on the tunnel interface, because it can inject any inner packet. The built client adds no inbound filter (Q7).
- The provider can use the refresh interval and per-user URLs as a presence beacon.
- Whoever supplies the link supplies the key. The link carries the provider's signing key, so a link from a stranger is a complete, valid subscription to the stranger's provider. The app shows the host and the key's fingerprint before any request, and cannot tell the two apart.
- A stolen signing key cannot be revoked for clients that still hold it. The provider can only rotate, and get a document that drops the stolen key to each client before the thief gets one to it.
- The provider can point its profiles at any public address, which clients then dial when their users connect. With many users that can be a third party's address, which then receives their connection attempts. The provider also chooses the server name a client sends in clear.

**Testing (planned):** fuzz targets `fuzz_subscription`, `fuzz_cards`, `fuzz_card_logo`, `fuzz_control_client`; UI tests that render a hostile corpus (markup, script, bidi overrides, zero-width characters, very long strings, homoglyph domains) and assert text-only output and visible truncation; a test that no control channel message changes the rating, kill switch or DNS pinning state; a test that a profile with certificate verification disabled is rated Unsafe.

**Built on the core side (B14).** A config reaches the core as a file, at start and on `SIGHUP`, or through an apply on the control API, which is a unix socket of mode 600 and nothing else: there is no remote listener, no token and no mTLS yet, so whoever can open the socket is the operator. What a later panel will meet is already there:

- The core parses and validates every document itself: strict JSON, unknown keys refused, at most 64 MiB and 8,000,000 JSON values, fixed limits on every list. Tests `strict_json`, `limits`, `a_document_of_too_many_values_is_refused_before_it_is_held_in_memory`, `the_user_and_rule_limits_validate_quickly`, fuzz target `config`.
- A document that does not validate, and a reload whose prepare step fails, leave the running config whole. Tests `an_invalid_document_changes_nothing`, `a_failing_prepare_changes_nothing`, `a_reload_that_fails_leaves_the_running_config_whole`, `a_stale_base_revision_is_refused_unparsed`.
- Errors name field paths, tags and names, never a value of the document. Test `secrets_never_reach_a_diagnostic_or_debug_output` for validation. The prepare step is read from code.

Not defended on the core side: a document that validates is obeyed. Whoever can write the config can remove the isolating rules, add exits and outbounds, turn on `log.destinations`, or add an `l3` exit, which turns on forwarding for the whole host. A reload also holds the flow table locked while every live flow is decided again (G31).

**Not defended:** inside its lifetime, a stolen session can do everything that does not require re-authentication: create users, read the user list and usage, change routing rules, disable users. A session stolen inside a re-authentication window can do the sensitive actions too. A leaked subscription link lets its holder enroll a device of its own while a place is free, and with provider-issued keys gives it the user's own device document, until the link is reset and those devices are removed. An attacker with code execution on the panel host, or on the admin's machine with a keylogger, is endpoint compromise (section 9). Encryption at rest does not help against an attacker who can read the running process. The gateway's private key sits on the panel host because it must be online: whoever takes it and holds recordings of subscription requests, from a content delivery network, a proxy that ends TLS, a relay mirror or a plain HTTP path, reads every request sealed to it since it was listed, and its answer, tokens and device secrets included. A switch every 180 days and retired keys destroyed after 120 days by default bound how much one key covers. After a theft with recordings, every account that sent a request under the key needs its token reset and a new link: the next key, kept off the host, helps only when the key is lost, or stolen with no recordings. The network on a plain HTTP path, and every party in front of the endpoint, still sees sizes and timing, and a plain endpoint's fixed request size is easy to match.

**Testing (planned):** an authorization matrix test that enumerates every route from the OpenAPI schema and asserts that only login, static assets and the subscription endpoint answer without authentication; a subscription endpoint test that an unknown token and an unknown path get identical bytes and the same response time distribution, that no session cookie is read or set there, that a body that does not open, an unknown key id, a request outside the window and a replay get the same bytes and timing as an unknown path, that a valid token always gets a signed answer sealed to its request, and that requests with device keys the endpoint has not seen cannot use up an enrolled device's allowance; `fuzz_sub_request`; a CSRF test per state-changing route; cookie attribute and CSP header assertions including `frame-ancestors`; a stored XSS corpus pushed through every writable field and through log lines, rendered in a browser test; session expiry and revocation tests; rate-limit tests, including one that a forged `X-Forwarded-For` from an untrusted peer does not change the counted source; a re-authentication test for each sensitive action; an SSRF test that points every fetchable URL at loopback, a private address, the node's own address, a name that resolves to them and a redirect to them; a rebinding test (wrong `Host`, cross-site `Origin` on a state change, on SSE and on WebSocket); a first-install test (no default login works, the one-time password stops working after first use) and a TOTP reuse test; an audit log test that every state-changing route writes exactly one entry and no route deletes entries.

### 5.6 Hostile peer inside the tunnel

A peer holds a valid key. It is a paying user, a stolen key or an attacker who subscribed on purpose. In config v1 a peer is a device of a user: the device has a public key and fixed tunnel addresses, and the user has groups, the list of exits it may leave through and optionally an expiry time.

**Assets:** AS12, AS10, AS8, and the provider's private networks behind the node.

**Capabilities:** sends arbitrary inner IP packets: spoofed sources, any destination, any protocol, fragments, malformed headers, IP options; opens many flows; floods; sends any control channel request; chooses the DNS names it asks for, and controls the answers for names in a zone it owns; keeps sending after its user was disabled or removed.

**Isolation is decided by rules now.** The first version of this document described one tunnel in which peers never reached each other, and never reached private ranges unless `allow_private` was set. That fixed property is gone. The node now does the following whatever the routing rules say, and leaves the rest to them.

Enforced whatever the rules say:

- A device sends only from its own addresses, in the tunnel the packet arrived through.
- A gateway address answers DNS on port 53, and ping from the devices of its own inbound (the node writes the reply, before any rule or exit), and nothing else. On a `veilway` inbound, and there only, the gateway of the inbound a packet came in through also answers the control channel on TCP port 47873 and takes that channel's MTU probes on UDP port 47873, before the routing rules the way gateway DNS is. The gateway of any other inbound stays a closed door (tests `the_channel_is_reached_from_the_device_s_own_address_on_its_own_inbound_and_from_nowhere_else`, `a_config_from_before_the_control_channel_is_served_as_before`).
- The destination gate: loopback, link-local (`169.254.0.0/16`, `fe80::/10`), the cloud metadata addresses outside link-local (AWS `fd00:ec2::254`, Alibaba `100.100.100.200`, Azure WireServer `168.63.129.16`, single addresses only, so private networks around them stay a routing decision), multicast, broadcast, unspecified and `0.0.0.0/8` never leave through any exit. Neither does an IPv6 address that carries one of those as an embedded IPv4 address (IPv4-compatible, NAT64 `64:ff9b::/96`, 6to4, Teredo by its server and by its client address), nor any IPv4-mapped address (`::ffff:a.b.c.d`).
- The node's own addresses are reachable by users by default. The routing set `host:self` names every address the host holds (read from its interfaces every 60 s and at each reload), and an operator who runs other services on those addresses (another VPN panel, a database, an admin port) adds `{"tag": "no-self", "ip": ["host:self"], "action": "reject"}` to `routing.rules` to refuse them, for every exit, door and node link. Nothing adds that rule for the operator.
- An address inside an inbound pool never leaves through an exit. It is delivered inside the node or refused.
- Broadcast and multicast are not carried, between users or outwards, and fragments are dropped.
- A flow leaves only through an exit in its user's `exits`.
- An answer reaches only the device whose live flow it answers.

The operator's responsibility:

- Whether users reach each other's devices. Without a `block` or `reject` rule that matches it, a packet to an address in a pool is delivered to the device that holds the address, on the same inbound or another one. The names `tunnel:users` and `tunnel:<inbound tag>` exist for such rules.
- Whether users reach private and special-purpose ranges through an exit. They are ordinary destinations unless a rule refuses them, and the name `geoip:private` stands for them. Through a `direct` outbound or an `l3` exit that means the networks the node host can reach, through a SOCKS5 outbound the networks the proxy can reach.
- Rule order. The first matching rule decides, so a rule placed before the isolating rules opens whatever it matches.

The shipped `config.example.json` starts its rules with one deliberate opening (devices on the `gaming` inbound reach each other) followed by a rule that rejects `tunnel:users` and one that rejects `geoip:private`. `veilway check`, and `veilway run` at start, warn when no enabled `block` or `reject` rule has `tunnel:users` in `ip` and no other condition, and again for `geoip:private`. The node starts anyway (G21).

**Not defended:** abuse of the exit against third parties (scanning, spam) beyond rate limits and whatever the provider adds; peers inferring that other users exist from shared load; a peer consuming its own flow and bandwidth allowance to degrade its own service; a config whose rules do not isolate users or do not refuse private networks, which the node warns about and then runs (G21); a rule placed before the isolating rules that opens more than its author meant, which no check finds; devices of one inbound degrading each other through the shared packet queues (G7); a user who owns a matching name steering its own flows through a `domain` rule.

**Testing:** the built tests named above, and the fuzz targets `packet` (the header parser every decrypted packet goes through, the same parser on the packet an ICMP error quotes, and the reset, echo reply and ICMP errors the node writes) and `dns` (both readers of the resolver). ### 5.7 Hostile upstream proxy

The upstream is the SOCKS5 proxy behind a `netstack` exit today, and later a chained node or a sidecar outbound. The DNS servers the node's resolver asks, through whichever exit the rules choose for the query, are upstreams in the same sense. For an `l3` exit the upstream is the host kernel and the network behind it (section 5.11).

**Assets:** AS3, AS4, AS10, AS8.

**Capabilities:** sees every destination and every byte that is not protected end to end; drops, delays, modifies and injects; answers SOCKS5 with anything, including a bound address of its choice, oversized or malformed UDP datagrams, forged DNS answers; holds connections open forever; flaps between working and failing.

### 5.10 Local network attacker (rogue access point, DHCP, ARP, local DNS)

The network the client is attached to: a public or rogue access point, another device on the same LAN, a compromised home router. It is a weaker position than the censor's on the path and a stronger one over the client's own network configuration.

**Assets:** AS3, AS4, AS9, AS1.

**Capabilities:** assigns the client's address, subnet, gateway and resolver; pushes classless static routes (DHCP option 121) and IPv6 router advertisements, at connect time and at any renewal after it; forges DNS answers before the tunnel is up; spoofs ARP and neighbor discovery; sees and alters everything that leaves outside the tunnel. | IPv6 router advertisements adding a route or resolver outside the tunnel | IPv6 from the client is dropped today. Once IPv6 is tunneled, the same firewall rule as for IPv4 applies. | Client engine | Dropping built (test `ipv6_packets_never_reach_the_server`). Tunneled IPv6 planned. |

**Not defended:** blocking, which this attacker can always do; everything the client sends before it connects (captive portal checks, the lookup of a node name where the profile carries a name and no address); the local network learning that the device runs a VPN and to which address; the traffic to local devices that the user let apps reach (invariant 24), which the network sees and can alter; a platform whose VPN API offers no firewall binding, where the profile is rated accordingly.

**Testing (planned):** a test network with a hostile DHCP server and resolver, with a packet capture on the physical interface, covering: a forged answer for the node name pointing at a third-party address (no packet to that address outside the transport socket), option 121 routes for a /2 and for a /32 pushed at connect and at renewal (no packet leaves outside the tunnel), a lease that declares a public /8 on-link (same), and application traffic addressed to the gateway (dropped). Run on every OS the client ships for.

### 5.11 Neighbors of a node that runs an `l3` exit

An `l3` exit is the one backend that touches the host: a TUN device, routes, an nftables table and, with `masquerade`, two host-wide sysctls. This subsection is about what that exposes, to the tunnel's own users (section 5.6) and to hosts on any network the node host is attached to.

**Assets:** AS10, AS12, and the networks the node host can reach.

**Capabilities:** a tunnel user sends any IP protocol to any address through the interface. A neighbor sends packets to the node host on any attached network, addressed to the host, to a tunnel address or to anything else, with any source address its network lets it use, and can use the host as its next hop.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| Privilege held by the node | An `l3` exit is the only place the node needs a privilege: `CAP_NET_ADMIN`, to create the TUN device and to run `ip` and `nft`. Without such an exit in the config none of this code runs. | `Running::start` in `l3`; one `unsafe` `ioctl` (`TUNSETIFF`) | Built. Linux only: on another system `run` refuses a config with an `l3` exit. |
| Command or rule injection through config values | The node runs the fixed programs `ip` and `nft` with argument lists, never through a shell. The interface name is limited to `[a-z][a-z0-9_-]{0,14}` by validation and checked again before it goes into a kernel request and an nftables rule. Pools are typed networks and the MTU an integer. | `run`, `Running::start` in `l3`, `Config::validate`. Validation test `exits_and_backends` | Built, read from code. No test asserts the character set of the generated arguments and rules (invariant 20a). Both programs are found through `PATH` (G24). |
| Tunnel traffic reaching the host itself: a service that listens on every address, the broadcast address of a network the host is on, an IPv6 anycast address | Without a `host:self` reject rule (opt-in) the engine carries traffic to the host's own addresses like any other destination; with one it refuses the unicast addresses an interface holds, which is all it can know: a public address that no interface holds (1:1 NAT) and an anycast address stay reachable, and so does a broadcast address. With an `l3` exit the node's own table `veilway_<interface>` drops everything that comes in on the interface for the host, with or without `masquerade`. | `hostaddrs`, the `input` chain written in `Running::start`. Test `without_masquerade_a_device_still_reaches_nothing_on_the_host_and_a_dropped_engine_cleans_up` | Built |
| Tunnel traffic leaving the interface back into it, around the engine's rules between users | The same table drops anything forwarded from the interface to the interface. | The `forward` chain written in `Running::start` | Built, read from code. The test above checks that the table holds its drop rules, not this path. |
| Packets aimed at a tunnel address from outside | What the kernel routes into the interface is delivered only to the device that holds the destination address, and only as the answer to a live flow of that device that left through this exit under the config in force: the flow's own reverse, or an ICMP error that quotes a packet of the flow. Everything else is counted (`NoFlow`) and dropped. | `Shared::returned`, `netstack::quoted`. Test `the_l3_exit_carries_every_protocol_through_the_kernel_and_cleans_up`, fuzz target `packet` | Built. The match is by addresses, protocol and ports. A neighbor that can route to the interface and knows or guesses those of a live flow can inject into that flow. |
| Host-wide forwarding | None that removes it. With `masquerade` the node turns on IPv4 and IPv6 forwarding for the whole host when they are off, says so at info, and sets them back when it stops. With `masquerade` off it changes neither, and forwarding and NAT are the operator's. | `Running::start`, `Undo` in `l3` | Built as described, and a residual risk (G22). |
| Host state left behind | A clean stop (`SIGINT`, `SIGTERM`, `Engine::shutdown`), a dropped engine, a reload that removes the exit and a reload that fails each take back the table and the sysctls. The device and its routes go when its last handle closes. A reload that fails after the old interface was closed brings that interface back. The next start removes a table a killed node left. | `Running::close`, `Drop for Running`, `Host::prepare`, `main` of `veilway`. Tests `the_l3_exit_carries_every_protocol_through_the_kernel_and_cleans_up`, `a_reload_adds_changes_and_removes_the_l3_exit_with_everything_it_sets_up`, `without_masquerade_a_device_still_reaches_nothing_on_the_host_and_a_dropped_engine_cleans_up` | Built. A killed node leaves forwarding on (G22). If both the new and the old interface fail to come up, the exit carries nothing until a reload succeeds, which is logged at error and read from code. |
| Two `l3` exits claiming the same pools | Refused at start and on reload: this build runs one `l3` exit per node. | `Host::prepare`. Test `a_second_l3_exit_is_refused_at_start` | Built as a refusal (G23) |
| Tunnel DNS for flows routed to an `l3` exit | With `masquerade` the node's resolver sends those queries from the host's own address, the way the exit's traffic leaves. Without it the exit carries no query of the resolver, and the node warns when the exit comes up. | `resolver::answer`, `Host::commit` | Built, read from code |

**Not defended:** while an `l3` exit with `masquerade` runs, the host forwards between all of its interfaces, not only from the tunnel. The node's table accepts everything except the two cases above, so any neighbor that uses the host as a next hop is forwarded unless the operator's own firewall says otherwise. Masqueraded tunnel traffic reaches whatever the host can route to, private networks included, unless a routing rule refuses it (section 5.6). A killed node (`SIGKILL`, a crash, power loss) leaves forwarding on. The kernel's forwarding and NAT code is trusted as it is.

**Testing:** the three tests in `crates/veilway-core/tests/l3.rs`, run by hand in a container with `CAP_NET_ADMIN` as the file header says. They are not part of CI, and the reviewer of the reload step read the `l3` reload paths without running them. Planned: a test with a second host on the node's network that uses the node as its next hop and aims packets at tunnel addresses, a test that a device cannot reach another device by way of the interface, and the character-set assertion of invariant 20a.

### 5.12 The Xray add-on

The add-on runs the pinned Xray-core as a child of a host process of its own. Xray listens on the public ports of its inbounds and sends their traffic only to a SOCKS5 hop that the node serves on `127.0.0.1`. That is where the node's policy lives, and not a restriction on Xray itself: the unit lets Xray connect to anything the host can reach, which the Xray outbounds of 5.17 need, so a compromised Xray is held by nothing but its user. This is boundary B9 of section 4, applied to a public listener and a parser that the project does not write.

**Capabilities:** anyone who reaches an Xray port can send Xray any bytes before any user is known. Whoever holds a user's Xray credential is that user at the hop, as with a tunnel.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| Xray gets the node's privileges, files or control socket | Its own system user `veilway-xray`, which cannot log in, under its own unit `veilway-xray.service`. The node reaches the host through a socket that only the node can open, and the node sends the document over it. `InaccessiblePaths` hides the node's folders. Xray gets an empty environment, `NoNewPrivileges`, and no capability unless a listener is below port 1024. Keys reach Xray in its document, never on a command line or in its environment. | `xray_units` in `scripts/veilway.sh`, `start` and `pre_exec` in `xray_host.rs`, `pem` and `generate` in `xray.rs` | Built. Gate checks Xray's user, capabilities, environment, reach and the absence of keys on its command line. |
| The executable is replaced or is not the pinned release | The installer checks the archive against a pinned SHA-256. The host opens the file once with `O_NOFOLLOW`, requires root ownership and no write bit for others on it and its folder, hashes that same descriptor and runs it from the descriptor. The node checks its own pin before each start. | `open_pinned` in `xray_host.rs`, `xray_pin` in `scripts/veilway.sh`, `PIN` in `xray.rs` | Built. Gate refuses an archive and an executable that do not match, and logs both refusals. |
| Users' traffic bypasses quota, gate, rules or exits | Xray's outbounds log in to the hop as the user. The hop answers CONNECT and UDP ASSOCIATE and applies the node's gate, entitlement, quota, rules, exits and counters. | `session` and `accept` in `xray.rs`, `associate` in `xray_udp.rs` | Built. Gate checks quota, disabling, rotation, rules and counters, over TCP and UDP. |
| Another local process uses the hop | The hop listens on `127.0.0.1` and requires a secret made new for each run. | `accept` and `session` in `xray.rs` | Built. See residual risk 1. |
| Another local process takes over a UDP association | Xray always asks for an association from `0.0.0.0:0`, so the relay's own socket is open to any process on the machine, and the first datagram would fix the association's peer. The relay therefore carries a datagram only from a UDP socket whose owner, read from the kernel's tables in `/proc/net` (`udp`, `udp6`), is the same user as the owner of the TCP connection that asked for the association (read from `tcp`, `tcp6`). It asks again for every source it has not placed yet, at most 20 times a second for one association, and drops and counts (`spoofed_source`) a source that is another user's, not found, or doubtful. A socket bound to the wildcard address (Xray's are, dual-stack on `::`) is matched by its port. An association is not granted at all when the owner of its control connection cannot be told, and where there is no `/proc/net` nothing is granted. The tables are read as untrusted: a size cap, strict lines, and a table with one line that does not parse says nothing. After the first datagram the association has one peer address and no other is let in. Each user holds at most 32 associations and 256 UDP flows, and the hop 4096 and 16384; a cap that the hop as a whole reaches is logged at info, once a minute at most. | `owner` and `lookup` in `xray_owner.rs`, `associate` and `Limits` in `xray_udp.rs` | Built. Unit tests for the table parser (IPv4, IPv6, mapped, malformed), integration tests with a source of another user, an unplaced source and an unplaced connection. Gate: the real lookup runs on every UDP check, Xray's user being another one than the node's, and a datagram sent to a live relay as a third user is not carried. |
| Xray logs client addresses | No access log, and the addresses in what it writes are masked. | `generate` in `xray.rs` | Built. Gate checks that no client address reaches the journal. |

**Residual risks:**

1. One hop secret per run. Every user's login to the hop carries the same secret, and the user name is not checked against anything else. Whoever learns the secret can act as any user until the node next starts. The secret is in Xray's document, which the host passes to Xray.
2. Xray parses public input before any user is known: the TLS handshake, the VLESS, Trojan and Shadowsocks headers, and the path to the decoy. A bug in Xray-core is a bug in code this project does not own. The release is pinned, Xray runs without privileges, its only way out is the hop, and its memory and task count are capped. A remote code execution in Xray would still give the attacker the hop secret and so every user's flows.
3. The relay cannot tell two processes of one user apart. A process that runs as the user of Xray, or that knows the hop secret and runs as the node's user, can send as Xray. A process of the same user can also take the source port of an Xray socket that has closed while its association is still open.
4. The shared address. Xray answers on the server's address next to the native profiles, so anyone who finds it can tell the server runs a proxy. Every native profile is capped at Detectable in the signed subscription document. Operators choose this when they add an inbound, and the panel says so.

**Testing:** `scripts/gate-xray.sh`, run by hand in Docker containers with the pinned Xray-core release. It is not part of CI and has not run on a real server. The gate does not cover `veilway.sh addon xray remove`, what a stranger gets on a Shadowsocks port, or the parser rows of section 6 for Xray's input. Those rows are not written yet.

### 5.13 Static mirror host

A provider may publish each device's signed document, sealed, on plain file hosting (subscription format page, "Static mirrors"), and the client fetches it with a plain `GET` when the endpoint and the relay mirrors have failed. The host is anyone the provider rents files from: a cloud storage service, a content delivery network, a code host, someone's web server. It runs no Veilway code and is not trusted with anything.

**Assets:** AS6 (it must never see a token), the documents of the devices, and the users' addresses and the times they fetch.

**Capabilities:** stores, lists and serves the files, keeps every version of every file for as long as it likes, and logs every fetch with its source address and time. It can delete files, serve old versions, serve any bytes, refuse to serve, or take the whole folder down. On a public host, everyone can list the files and read their history.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| The host reads documents or the token | A static fetch is a `GET` of a file name and carries no token, device secret, device key, cookie or conditional field. A file is sealed with ChaCha20-Poly1305 under a key derived from the token and the device secret, and has no magic, no version and no length in the clear. | "Keys of a static mirror", "The file" | Planned |
| The host serves a forged, swapped or old document | The opened envelope goes through the same checks as an answer from the endpoint: signature under a key held, identity, serial, expiry. The file's name, which holds its period and base URL, is in the associated data. An old document is refused by its serial or is no newer document, and a static answer is never a successful refresh unless a newer document is accepted. | "How the client opens a file", "Order and rate" | Planned |
| A missing file is read as a revocation | A 404 or any failure of a static mirror is a failure of that mirror, and the client tries the next place. Only a signed refusal says an account is off. | "How a client fetches a static mirror" | Planned |
| The host follows one device over time by its file name | A file name holds for one period of 604,800 s, and every name of a folder changes in the same round. Names differ per base URL, so two hosts cannot match files by name. | "Periods and clocks" | Planned |
| The file list counts users or marks a reset | One size per folder, every file rewritten in every round into a directory swapped in whole, and decoys per period and folder, born and dying independently within a range. | "Publishing" | Planned |
| A later leak opens the history a host keeps | Published documents carry no `usage`. Every host is taken to keep every version. | "Which files exist", "What the host keeps" | Planned |
| The client fetches more often or from more places | A static host is confirmed by the user before it is contacted, a refresh makes at most one `GET` per static mirror, and the rules for when a fetch happens are unchanged. | "Order and rate" | Planned |

**Not defended:**

- Within one period, the host's logs tie every fetch of a device to one name, with the address it came from: the device's own address outside a tunnel, the provider's exit through one. Across periods, the host can still follow a device by its address or its habits of time. Per-period names limit the record to a week and a reset of the link ends it. Fetching through a tunnel hides the device's address and shows the host the provider's exits instead.
- The host keeps every sealed version. `k_mirror` is fixed for the life of a token, so whoever later holds the link and the device secret (a copy of the device's storage, or whoever holds the gateway's private key and recorded a request of the device) opens every version kept, with the transport secrets, profiles and device names of their time. Leaving `usage` out limits what that gives. A key that moves forward per period is an open question in the spec.
- A burst of fetches tells the host that the provider's endpoint is failing for many users, and from where.
- Decoys hide nothing from the host itself: its logs show that no client fetches them.
- A host name that only the provider uses (its own domain, `name.github.io`, a bucket under its own name) is blocked at no collateral cost. Only a shared host name with the folder in the path costs the censor something. The panel warns about every base URL whose host is not on its list of shared names.
- Until the client's TLS offers `h2` and a browser's HTTP/2 settings (G61), and while the subscription fetch has the gaps of G63, a static fetch's handshake is not a browser's, and that separates it from other traffic to a shared host.
- A folder of random names of one size, all rewritten on a schedule, is a pattern a host can scan for and ban.

**Testing (planned):** the tests of the subscription format page for static mirrors, the fuzz target `fuzz_sub_mirror` (section 6, row 57), and vectors for the derivation and one sealed file computed apart from the implementation.

### 5.14 Borrowed third-party site (`faketls`, designed, not built)

The `faketls` transport (Borrowed-site mode page in `veilway-docs`) holds no certificate and borrows a real site chosen by the operator. A client proves itself inside its ClientHello. Everyone else is relayed byte for byte to the site, so a prober sees the site's own handshake. Nothing here is built. The mode ships as alpha: off by default, labeled alpha in the panel and the apps with a warning that it is new and unreviewed, and without outside review. Every row is a design, not a result.

**Assets:** AS2, AS4, the node transport key of the `faketls` transport, and the borrowed site as a third party that can be harmed.

**Capabilities:** the censor of section 5.1, and the site itself. The proof is in clear on the path, so the censor's own passive log holds every hello.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| Blocking by SNI | The server name is the borrowed site's. The node holds no certificate and no name of its own. | `faketls` | Designed, not built |
| Active probing | Everything that is not a user's hello is relayed to the site, and the prober sees its handshake, certificate and close behavior. A hello whose carrier opens is never relayed: it gets a flight the node makes, sized and timed from the site's answer to those same bytes, so a recorded user's hello sent again cannot be compared with the user's own flight. | Borrowed-site mode: "Strangers", "What the node answers with" | Designed, not built |
| A paired comparison with a budget that is spent or a site that is down | Kept samples of at most 32 shapes, padded to the site's lengths, and the node never refuses a user for the budget. A statistical comparison then works again, and a censor can drain the budget on purpose. | "The flight", "What remains detectable" | Designed, not built. Listed under Not defended. |
| Replay of a recorded hello | The key share of the hello is recorded in the replay cache under kind 1, a hello refused by a limit is recorded too, and a copy gets a flight with a random leaf from which nothing can be read. | "Verifying", "Probes and replays" | Designed, not built |
| The proof is readable by whoever holds the transport key | The transport key of `faketls` is its own and is refused if equal to any other transport's, so a leak of it opens nothing of `tls`. The device tag is of the hour, so recorded hellos link only within an hour. | "Keys" | Designed, not built. Listed under Not defended. |
| A reused ephemeral key breaks the sealed carrier | A fresh `x` for every hello, from the system random source, and a backstop list of the last 4,096 seals. | "Sealing" | Designed, not built |
| The borrowed site is harmed | The operator chooses the site and must acknowledge the effect (`site.acknowledged`). Connections to the site are capped per source, in total and per second. Nothing of a user's later records, of the tunnel or of the keys reaches the site. | "The third party" | Designed, not built |
| The node's own address is what the site sees | `site.outbound` names one of the node's `outbounds`, and then every connection the node makes to the site (strangers, probes, a user's early connection) leaves by it, through the same dial an exit with that outbound uses. A down outbound fails those connections with its reason in the log and never falls back to the node's own address. Trade-off: the extra hop adds latency to the relay and to the live copy, which makes the node easier to tell from the site, and a site may refuse addresses that are not its usual ones. | "Config and profile fields" | Built, alpha. Tests `the_connections_to_the_site_leave_by_its_outbound_and_by_no_other_way`, `an_outbound_that_is_down_fails_the_connections_to_the_site_and_never_falls_back_to_the_nodes_own_address` |
| The site changes its behavior | The node probes the site at start, on reload and every 6 h, keeps the last 32 shapes none older than 7 days, and after 24 h without a successful probe relays everything. | "The shape of the site" | Designed, not built. Hours of a wrong shape remain. |
| A holder of a subscription tells the node from the site | None. A holder of a profile can compare the node's flight with the site's. | "Probes and replays" | Not defended |

**Not defended:**

- The node's address is not the site's, and the path to it is not the site's path. One lookup of the name, or a measurement of the round-trip time or time to live against the site from the same place, shows it.
- A holder of the `faketls` transport private key opens every recorded hello, learns the time and source of each connection and can answer a client as the node, until profiles carry a new key. The tunnel stays protected by WireGuard.
- A site that changes faster than the probes, and a flight made from samples when the live answer is missing.
- Closing under load: a censor that fills the budget for new connections to the site makes the node close strangers where the site would have answered. Users are still served.
- Everything that `tls` and `ws` do not hide about the flow after the handshake.
- The site's owner, who may notice and object, and a law or terms that forbid it.

**Testing (planned):** the twelve tests of "Tests before it is offered" on the Borrowed-site mode page, among them the paired comparison with a classifier, the relay test of half-close and reset, the budget test, the seal test and the fuzz target `fuzz_faketls_clienthello` (section 6, row 5).

### 5.15 Upstream provider

A node may use another provider's Veilway subscription as the carrier of an exit (`upstreams` in the config, an exit with `{"type": "upstream"}`, the Upstreams page in `veilway-docs`). The client engine runs inside the node for one device of that subscription, and a `chain` link sits behind it. The users are not asked: the operator adds a second provider to their path, and says so to them. The provider is the adversary here. Its document, its transports, its control channel and every packet it returns are hostile input.

**Assets:** AS3 and AS4 (what the exit carries), AS5 and AS6 (the node's device key and secret for that provider, and the account's link), AS12, and the node host with its networks.

**Capabilities:** sees every destination, DNS name, unprotected byte and timing of the flows routed to it, the node's address and one device. It does not see users, their tunnel addresses or keys. It can send any packet, any signed document, any control message and any dial address, cut the device off, refuse it, let the document run out, or answer wrongly.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| **U1** The provider sends packets to users or the node | Whatever the tunnel yields goes to `chain_back`, which delivers only the answer to a live flow of a device routed through this exit, and drops and counts the rest. While the carrier is not up, nothing is delivered. | `chain_back` in `chain.rs`, `drive` in `upstream.rs` | Built. Test `a_hostile_provider_reaches_no_user_and_a_user_reaches_no_gateway_of_it`. |
| **U2** A user's flow reaches the engine's own channel at the provider's gateways | No flow routed to the exit reaches a gateway of the profile in use, on any port, over the tunnel, the resolver or the Xray hop. A gateway is refused for the flows of its own exit only, since the provider names it. | `reaches_upstream` in `plan.rs`, `inbound.rs`, `resolver.rs`, `xray.rs` | Built. Same test. |
| **U3** The provider steers the node's dials at the node host or its networks | Every dial address of the profile is refused if it is loopback, link-local, multicast, unspecified, IPv4-mapped, an inbound pool, an address of the node itself, or private or shared unless `allow_private`. This runs before the engine sees the profile, at every start and whenever a refresh changes the profile's keys, addresses or candidates. A profile with one refused address is not used at all. Profile failover (`failover`, or no `profile`) gives the provider no way round this: every profile it lists is held to the same checks (the dial addresses, the datagram check for a socks5 `via`, the class the operator allowed, the chosen `transport`) before `Tunnel::start`, one that fails is skipped and the next is checked the same way, and a profile that is skipped is shown to the operator with a reason and never with an address. | `forbidden`, `dialable`, `attempt` and `drive` in `upstream.rs` | Built. Tests `a_profile_that_points_the_node_at_a_forbidden_address_or_a_way_the_operator_did_not_allow_is_not_used` and `an_unreachable_profile_gives_way_to_the_next_and_a_pinned_one_does_not`. |
| **U4** The provider changes routes, addresses, resolvers or the exits the node's users see | The only value taken from its control channel is a lower MTU, inside 1280 to the profile's MTU (a profile below 1280 keeps its own). Exits (their names, country codes and selection), usage, the period and the account's end, notices with their severity, the profile names of the document and the state the tunnel reports are shown to the operator as plain text, cut, without control and direction characters, and a name is never used as a tag or a path. Nothing else is applied: the operator's choice of exit is made by tag, and a tag the provider does not offer is refused, never matched by name. | `lower` and `judge` in `upstream.rs`, `plain` | Built. Test `a_lower_mtu_of_the_provider_is_taken_and_a_larger_packet_gets_the_size_back`. |
| **U5** A flow routed to the exit leaves another way | It leaves through the provider or is refused as unreachable, counted. No fallback to the provider's default exit, to another exit of the node or to a direct dial. With `exit` set, a provider that does not offer it or refuses it takes the exit down. Only `routing.fallback`, which the operator wrote, moves a flow, and `veilway check` warns when it is set beside an upstream exit. The Xray add-on cannot use the exit. **Live switch:** the operator may change `exit` on a running upstream without a new tunnel (the host keeps the task when only `exit` differs and calls `want`). The carrier stops carrying in that very call, so it refuses what is routed to it as when it is down, and it carries again only once the provider says the exit asked for is the one selected for the device. A return to the provider's default is the same: the carrier waits until the provider has dropped the device's selection. Nothing leaves through the old exit in between, and a task that is replaced for any other change takes the carrier down before the new one starts. | `phase`, `want`, `judge` and `drive` in `upstream.rs`, `commit` in `host.rs`, `chained` in `chain.rs` | Built. Tests `a_provider_that_removes_the_device_takes_the_exit_down_with_no_fallback_and_it_comes_back` and `a_new_exit_is_taken_on_the_running_tunnel_and_nothing_leaves_the_old_one_meanwhile`. |
| **U6** Upstream secrets leak | The link, the device key and the device secret are `Secret`s of the config, redacted on read, never in logs, the API, events or the status. The state file holds the signed document with the per-device transport secrets, mode 600, refused if group or others can read it, not owned by the node's user or not a regular file. A removal takes the document and keys out of it and leaves a mark (tag and binding, at most 8) so the device is not enrolled again. | `upstream_state.rs`, `config/` | Built. Fuzz target `upstream_state`, canary scan in `tests/upstream.rs`. |
| **U7** The provider uses up memory, time or the operator's attention | At most 8 upstreams, 4 previews for 10 minutes counting fetches still running, a bounded queue to the tunnel, a bounded document and state file, 8 notices of 200 characters, 16 exits of 64. A refresh waits 1 h to 24 h (the document's interval, plus up to 20% jitter), an hour for the first day of trouble and a day after that. A failed step doubles its wait from 30 s to an hour. **Enrollment and removal.** The operator sees a provider in three steps: the link and its key fingerprint, a fetch from the node that shows the verified document, and a confirmation with re-authentication (invariant 32). The fetch takes a place at the provider, so a preview that is declined or not answered in 10 minutes gives the place back. Removing sends `leave` for at most 10 s. The document stays until the provider confirms, so the same call can tell it again. A removed upstream is not run again across restarts until a config without it, or with another link or device, is in force. A reload that drops an upstream never sends it.

**Not defended:**

- The provider sees what the exit sees. There is no anonymity from it, and it can correlate the flows of all the users routed to it.
- DNS answers and unprotected content from the provider can be forged. The node's resolver asks through the exit, so it trusts the provider's answers.
- Availability. The provider can cut the exit, and the exit is down until it lets the device in again.
- With no `exit` set, the provider's own default exit is used, and the provider chooses it.
- A user who is routed to the exit is not told by the protocol that it belongs to a third party. The operator's disclosure does that.
- A flow to a provider gateway through another exit is the other exit's business, not this one's.

### 5.16 Proxy inbounds

A node may serve `socks5`, `http` and `mixed` inbounds (`inbounds` with those types, and `proxy_password` on a user), which let other software use it as a plain proxy. They are listeners with no cover: nothing about them looks like a web site, and nothing in them is encrypted. Every connection logs in as a user with that user's name and `proxy_password`, and from then on runs the code the Xray hop runs after its login (`xray::connect` and `xray::relay`, and `xray_udp::associate` for UDP), so the destination gate, the rules, the user's exits and entitlement, the quota and the counters are the tunnel's. This is boundary B9 of section 4 for a listener that outsiders can reach.

**Assets:** AS3 and AS4 (what goes through is in the clear on the way in), AS5 (the proxy passwords, which are secrets of their own and no key of the tunnel), AS2 (a proxy port is easy to find and block, and says what the node is), AS10 and AS12, and the networks the node host can reach.

**Capabilities:** anyone who reaches the listen address can send it bytes before any login, up to the caps below. Whoever is on the path reads and changes everything: the password, every destination name and address, and the content. Whoever holds a user's password is that user on this inbound, with the user's quota and exits, and can open as many connections as the user's limits allow. The listen address is public only when the operator wrote `public: true`.

**Not defended:**

- Everything P1 says. A proxy inbound is rated like a plaintext transport would be: nothing in it hides the node or its users from the path, and a censor that finds the port can block it and learn what it is.
- A user's proxy password is a password: whoever learns it is the user on every proxy inbound that admits them until it changes. It is sent in the clear on the way in (Basic on HTTP, RFC 1929 on SOCKS5).
- What a user does through the node is the operator's to see, as with the tunnel (section 9, item 3).

**Residual risks:**

1. An operator who sets `public: true` has chosen to send passwords and traffic across the network unencrypted. The validation warning and the docs say so, and nothing else stops it.
2. Guessing from many sources. The block is for a source and a name: an attacker with many addresses guesses at 10 a minute from each, and an IPv6 attacker with many /64s too, slowed only by the wait that grows with the failures to the name (2 s at most for a refusal; a right password never waits). Each table keeps 4,096 entries and gives up the lowest counts first and never a blocked one, so floods push out only counts that are small; a table that is full of blocked entries keeps no new one, which takes 4,096 sources that each failed ten logins. Behind a loopback front every user shares one source, which is why loopback is not blocked, and then only the wait holds. Passwords are long, but a user who is given a short one by hand is covered only by validation's 16 characters.
3. UDP has no login of its own. A datagram carries no proof of who sent it. On a loopback inbound the user id of the socket's owner ties it to the connection, so another user of the host cannot take the association, but a process of the same user can. On any other address only the address and port the client gave decide: a sender that can forge them and knows the relay's port can inject datagrams until the association ends and sees nothing back, and a process on the client's own host that learns the port first can send from it too. Clients that send `0.0.0.0:0` in the request, as many do, get no association on such an inbound unless the operator turns `udp_any_port` on, which brings back the window before the client's first datagram, in which a sender that shares the client's address (neighbours behind the same carrier NAT) can take the association.
4. A login names a user by the user's name, which is the username on the wire, and a quick scan of the user list answers a name that does not exist a little sooner than one that does.

### 5.17 Xray outbounds

A node may carry an exit through a VLESS, VMess, Trojan or Shadowsocks server of another party (`outbounds` of type `xray`, behind a `netstack` exit). The add-on's one Xray process runs a `trojan` inbound for each such outbound, listening on a Unix socket and routed to that outbound only, and the node connects to that socket and speaks Trojan (CONNECT for TCP, one framed stream for each UDP flow). So the exit, the gate, the rules, the quotas and the counters are the ones every flow meets, and this section is about the two new edges: the provider's server, and the socket. It builds on 5.12, whose user, pin and host stay as they are.

**Assets:** AS3 and AS4 (what the exit carries), AS5 (the provider's server address and the credential of the outbound, which are the operator's secrets and a provider's customer account), AS2 (the node's address as the provider sees it), and the node host with its networks.

**Capabilities:** the provider sees the node's address, every destination name and address of the flows routed to it, and every byte that the destination's own protocol leaves unprotected, as for any exit (5.15, "Not defended"). It does not see users, their tunnel addresses or keys. It can answer anything on the connection Xray makes: a hostile server can send any bytes to Xray's client side, which Xray parses. A process on the node host can try the socket of an outbound, if it can enter the folder, which only the node's user and Xray's can. A person who reads a share link before the operator pastes it knows the credential in it.

| **X6** A hostile provider attacks Xray's client side | Xray is the pinned release and runs as `veilway-xray` with nothing of the node's (5.12). The provider's bytes meet Xray's client code and nothing of the node's before Xray has handed them on as the stream of a SOCKS5 CONNECT or as datagrams. Certificates are always checked against the system roots: no key turns that off. | `xray_host` | Built. See residual risk 2. |
| **X7** A change of an outbound cuts users off | One Xray runs for the inbounds and the outbounds, so a change of either restarts it, after two seconds without another change. Connections of Xray inbounds and flows through its outbounds end and come back with the next connect. No quota, count or user is lost, since all of that lives in the node. | `xray::run` | Built. The cost is chosen: a second process would need a second lease, and the host serves one at a time. |
| **X8** Xray's own egress goes somewhere it should not | The Xray unit is not restricted in what it may connect to: it has the network of the host (`AF_INET`, `AF_INET6`, no `IPAddressDeny`), because the providers' servers can be anywhere. What keeps it to the provider is the document the node writes, in which an outbound has one address the node checked, and nothing in Xray resolves a name. A bug in Xray is not held by the unit to that address. The route to the provider is the host's, so on a host with other tunnels it follows the host's routing table, and the `interface` and `bind` of the config do not apply to it. | `parts`, `xray_units` in `scripts/veilway.sh` | Not defended, and said here, in 5.12 and in the docs. |

**Not defended:**

- The provider sees what the exit sees. There is no anonymity from it, and it can correlate every flow of every user routed to it. DNS answers and unprotected content from it can be forged.
- The provider's server is a third party's software, and Veilway does not rate its protocol. A VMess or Shadowsocks server with a weak cipher is as weak as the cipher is; the table of the client refuses the ciphers it lists as weak, and the typed form accepts the same list.
- Availability. The provider can cut the exit, and the exit is down until Xray carries it again.

**Residual risks:**

1. Xray parses the provider's bytes. A bug in Xray-core is a bug in code this project does not own. The release is pinned and runs without privileges, but a remote code execution by a hostile provider would give it the passwords of every Xray outbound, every Xray inbound's hop secret (5.12, residual risk 2), which is every user's flows, and the network of the host (X8). Use a provider the operator trusts at least as much as the node's users.
2. The node and Xray share a folder through a group. A process of the node's user or of Xray's user can use the sockets (they know the passwords, or are the node). Another user of the host cannot enter the folder. Where the folder is made with a wider mode, `veilway doctor` fails.
3. Xray is given the address the node looked up, so a name cannot lead Xray somewhere the node did not check. The address can change between two lookups, and for up to 15 minutes Xray dials the one the node found.
4. Socket files are removed by Xray when it closes them. After a kill the files of that start stay in the folder until the unit stops and the runtime folder is removed; their names are never used again, since every start makes new ones.
5. Trojan has no reply to a request. A destination that does not connect shows only as a stream that ends, so the exit's health for Xray outbounds comes from the hop (socket, Xray running) and not from refused destinations.
6. Only Linux nodes run the add-on host. On macOS and Windows nodes there is no Xray outbound: its hop says the add-on runs on Linux only. Unix sockets and `SO_PEERCRED`-style checks exist on macOS, but the host does not, and the add-on is not offered there.

**Testing:** `crates/veilway-core/tests/config_xray_outbound.rs` (config, links, secrets), `tests/xray_outbound.rs` (a node in the process with a stand-in for the host that makes the sockets), and the unit tests of `engine/xray_out.rs`, `engine/xray_trojan.rs` and `engine/xray.rs`, the last of which runs the pinned Xray against a VLESS server and loads every kind of stream and security the node writes into it when `VEILWAY_TEST_XRAY` names the executable (not run in CI). Not yet reviewed by anyone outside the project.

### 5.18 The local proxy of the apps

The desktop app, the Android app and `veilway connect` can run a local SOCKS5 and HTTP proxy (`veilway_engine::local`): either in place of the system VPN (proxy only), where each connection is opened inside the tunnel by a userspace TCP/IP stack and names are asked of the node's resolver, or next to a running VPN, where connections are opened with system sockets that the VPN carries.

**Assets:** AS3 and AS4 (what the proxied programs send and to whom), the fact that the device uses Veilway and which server (AS2), and the device's own networks and services.

**Capabilities:** any program on the device can connect to a loopback port, and an Android app needs only the internet permission to do so; apps in censored countries scan local ports for proxies to detect VPN use. With "allow devices on my network", anyone on that network can reach the port. The traffic between a client and the proxy is not encrypted.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| **L1** Another program or app uses the proxy, or detects through it that the device runs a VPN and to which server | Every connection logs in by default, also on loopback: the apps make a random user name and password the first time the proxy is turned on (`LocalProxy::random_login`). Android always requires the login. Desktop lets it be turned off only for 127.0.0.1, behind a warning | `ProxySettings::ensure_login`, `LocalProxy::check` | Built |
| **L2** A proxy reachable from the network is open | A listen address that is not loopback is refused without a login, by the engine and by the apps, and the apps confirm before opening it, saying the traffic is not encrypted | `LocalProxy::check`, the settings dialog | Built |
| **L3** A login is guessed | Logins are compared in constant time. A source that fails five times in a minute is refused for the rest of the minute, checked again before each login, and at most 20 failed logins a minute are taken from all sources together. Loopback sources share one address and count only in the global limit, so one hostile local app cannot lock the others out | `local.rs` login table | Built |
| **L4** A name leaks to the local network in proxy-only mode | Names are resolved only inside the tunnel, by A and AAAA queries to the gateway; the system resolver is never asked. The cache is cleared when the exit changes or the session is not connected | `local_stack.rs`, `local_dns.rs` | Built |
| **L5** Traffic leaves outside the tunnel next to a VPN that dropped | The alongside mode watches the tunnel's status and refuses new connections while it is not connected; the platform's kill switch stays the main guard | `Local::alongside` | Built |
| **L6** A proxy client reaches the device itself or its network | Loopback, unspecified, multicast, broadcast, port 0 and the stack's own addresses are refused, for written addresses and resolved names. Next to the VPN, link-local (with 169.254.169.254), the listener's own address and private ranges (RFC 1918, 100.64/10, fc00::/7) are refused unless `allow_private` is set. Other public addresses of the host are not enumerated | `allowed` in `local.rs` | Built, gap noted |
| **L7** The proxy exhausts the device's memory | Connections and stack flows are capped at `max_connections` (256), 32 per source on a network address, smaller socket buffers, a handshake deadline of 10 s, socket timeouts of 60 s and an idle limit of an hour in both modes | `local.rs`, `local_stack.rs` | Built |
| **L8** Logs on a seized device show where the user went | The proxy logs no destination names and no login; `LocalProxy` has no `Debug` and the apps' settings hide the password from `Debug` | `local.rs`, `proxy.rs` | Built |

**Not defended:** a program the user points at the proxy sees its own traffic, as with any proxy. SOCKS5 UDP ASSOCIATE and BIND are refused. On desktop the password is in the app's settings file (mode 600 on Unix), readable by the user's own programs; on Android it is sealed with a Keystore key.

### 5.19 Several nodes from one panel

Designed for v0.3.0, nothing of it is built. One panel may manage several nodes. The node next to the panel stays on the control socket (B8) as node 1. Every other node is a remote node, joined to node 1 by a node link (`protocol/node-links.md` of the docs) that both operators marked for management at pairing: `manage: "peer"` on node 1, `manage: "by_peer"` on the remote. The panel still talks only to node 1. Node 1 gets one new control API route, `/v1/links/{tag}/api/{path}`, which opens a TCP connection inside that link's WireGuard session to a management port (47874) on the remote's in-link address. The remote answers it from its own control API router, restricted to a fixed list of routes. Nothing new listens on any network interface and there is no new cryptography. The wire details are in `protocol/panel-nodes.md` and the "Management" part of `protocol/node-links.md` of the docs.

**Assets:** AS5 (users' identities and device public keys on each remote node, per-node transport secrets, proxy passwords and Xray secrets, the links' keys), AS7 (the panel and node 1, which control every managed node), AS12 (isolation between users, now also between nodes). One quota per user across nodes counts as an asset too.

**Capabilities considered:**

- A scanner or a network attacker who probes a node for a management port, or who reads, drops, delays or changes the link's packets (they see what any link shows, see 5.6 and the node-links page).
- A remote node's operator, or whoever seized it, with its config and everything it holds for its users.
- Another operator's link to the same remote (a remote used as an exit by someone else), and a user of either node.
- A stolen node 1 or a compromised panel.
- A node that lies in its answers and in its usage numbers.
- Someone in the middle of the pairing who adds or drops `manage` in the codes.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| **M1** A scanner finds a management port on a node | There is none on any interface. The control API stays on its unix socket. Management is a TCP port inside one link's WireGuard session, answered only to that link's peer, on the link's own address. A packet that is not from that session never reaches it. | `engine/manage.rs`, ingress hook | Designed |
| **M2** Someone other than the panel's node calls a node's API through a link | A remote serves management only while its own config says `manage: "by_peer"` on that link, only to that link's WireGuard peer (the session decides who is calling, not the source address), only on the link address and port. A link of another operator to the same node has another link index and is never served. At most one `by_peer` link per node. | `Link.manage`, `plan.link_of`, config validation | Designed |
| **M3** A seized remote node calls in, or reaches node 1 or another node | Trust is one way. Node 1 opens connections and never accepts one: it has no listener, and a SYN from the remote to node 1's link address is dropped as any other packet to a link address is. A node with a `by_peer` link may have no `peer` link, so a managed node is never also a managing one. The relay route exists on node 1's unix socket only, and a managed node refuses it through a link. | Hook (client side only on `peer`), validation, allowlist | Designed |
| **M4** Management is added to a link without the managed operator's consent, or removed on the way | `manage` and the listener address are members of the offer code, so the pairing hash and both fingerprints cover them. A code changed on the way shows as two different fingerprints. The managed side consents in words: `veilway link offer --managed`, or a prompt that names what the other node will be able to change and needs `yes` typed. A node older than v0.3.0 refuses the member. `manage` is refused on a link with an upstream carrier. | `pairing.rs`, `veilway link` | Designed |
| **M5** A user flow or another link is mistaken for management, or the reverse | The target is a link address, which is never a user destination on either node (refused at both), and answers come from a link address, which no user flow has. Management packets never enter the flow table, the entry's address translation, quotas, the link's flow cap or the rules. A managed link always has both addresses, whatever its direction. | `plan.linked`, hook placed before the entry half's early return | Designed |
| **M6** The managing side can do more than the panel needs | A fixed allowlist of the routes the panel calls today, checked on node 1 and again on the remote: config read and replace, validate and diff, users and their usage and reset, stats, sessions, exits, inbounds, links, upstreams, replay reset. No events stream, no OpenAPI route, and never the relay route itself. A route or method off the list is refused with its own code on both nodes. It is still full control of that node's process through its config: users, inbounds, exits, outbounds, links, upstreams. Secrets stay redacted in answers, as on the socket. It is not a shell. | Allowlist, `veilway-api` | Designed |
| **M7** The managing side exhausts the remote or its link | Four management connections at once per link on each side, 4 MiB request body, 8 MiB answer cap, 256 KiB of window per connection, a 10 s connect wait, the API's request deadlines, and counters for connections, refusals and bytes. The managing node runs eight relays at once across all its links; a ninth waits 5 s and is answered `busy`. User traffic on the link is not slowed by management (tested with a 4 MiB transfer). | Limits table of the docs page; `Limits::relays` | Designed. The numbers are judgement calls. |
| **M8** A push through the link strands the remote | A config for the remote that arrives through a link is refused at once when the managing link is missing, disabled, or changed in its id, `direction`, keys, addresses, `manage`, `transport_secret`, `inbound` or `peer`, or when the inbound the link is carried by differs in any part (its key, transports and listen addresses). Every other pushed config is applied on trial: the remote keeps the previous document and puts it back after 120 s unless a request comes through the same link at least 10 s after the push, over a WireGuard session made after the push. Node 1 makes its session of the link again at once after the push's answer, and a remote that dials the link does so 2 s after the push, so a config that breaks the next session cannot be confirmed by requests on the old one. The previous document is kept in `config.json.trial` next to the config (mode 600, with a digest of the pushed document) until the trial ends, so a restart before then puts it back, unless the config file was changed since the push. This catches what the first rule cannot judge (the `via` outbound, DNS, an MTU that breaks the path). The one exception is "Remove node" (M15). | Guards 1 and 2 of the design; `manage.rs` (`gate`, `on_trial`, `restore_trial`) | Designed |
| **M9** Management traffic and user traffic damage each other | Management is separate from user flows by address (M5), by its own connections and caps (M7), and by counting: it appears in the link's traffic counters and in its own counters, never in a user's usage or the flow table. A user cannot reach a link address, so no user can address the management port. | Hook, `State` counters | Designed |
| **M10** A remote node answers with hostile data | Every answer is untrusted panel input: size cap, strict JSON, strings shown escaped. Only the status, `etag` and `content-type` headers cross the relay, in either direction, so the answers node 1 gives itself on the relay route carry `veilway-relay: node1`, which a remote cannot set. A relay answer that is not HTTP/1.1 or is too large resets the connection. | Relay route, panel `request` | Designed |
| **M11** A seized remote node exposes users on other nodes | Transport secrets, proxy passwords and Xray client secrets are derived per node (HKDF of the stored secret with the node's own random uid, so re-pairing a link changes no secret). Remote nodes see opaque user names (HMAC of the panel's secret key, the node uid and the user's record id), and node 1 keeps real names. Device private keys never exist on nodes (invariant 30). | Panel `fill`, per-node derivations | Designed |
| **M12** A seized or lying node cuts users everywhere with false usage, or hides real usage | Counters are absolute, so a repeat changes nothing, and a counter that falls inside a period is banked. Growth per poll is capped at the node's maximum rate times the time since the last poll (default 1.25 GB/s), clipped and logged. Usage is shown per node, and an admin can stop counting a node. | Panel `node_usage` merge, per-node `max_rate`, `counted` | Designed. A node can still report less than it counted, which only lets users pass the quota. |
| **M13** Quotas pass the limit, or the cut shows the wrong reason | Every node enforces the user's full quota locally, as a backstop that holds while the panel cannot reach it. When the panel's sum reaches the quota, it writes `quota_bytes = max(1, that node's used_bytes)` for that user on every node, and each node cuts the user itself with the quota reason. At the next period each node's own count restarts, which lets the user in, and the panel writes the full quota again. | Panel sync, `engine/usage.rs` unchanged | Designed. The overrun is accepted, see "Not defended". |
| **M14** A down or blocked node blocks changes to others, or serves forever on stale rights | Node 1 reports each link's state, and a link that is not Up answers 503 at once, so the panel skips it without waiting for a timeout. Each node has its own lock, dirty flag and backoff. A node that cannot be reached keeps serving its last config, including its local quota and expiry, and the panel shows "out of date since". A down node gets the whole users list at its next sync, never a diff. Node-scoped edits wait for the node. Users, devices, quotas and resets never wait. | Panel upkeep, relay route | Designed |
| **M15** A removed or taken node keeps its users or its access | "Remove node" first asks the remote, through the link, to apply a document with no users and without the managing link (the one change the first guard of M8 allows, not put on trial), then removes the link from node 1. The remote writes that document to its config file and drops any trial before it answers 202, and puts it in force 10 s later, once the answer has gone back through the link it removes: a restart in between comes back emptied, never with the users. A lost answer may still have emptied the node, and the panel says to remove it as taken. "Taken" skips asking and only removes the link on node 1: after that nothing the node sends is served and nothing is sent to it. Either side can also remove the link from its own config, which ends management at once. | `DELETE /nodes/{id}`, link removal | Designed |

**Not defended:**

- A compromised panel or node 1 controls every managed node. Removing a link on the remote is the remote operator's only answer.
- A remote node sees its users' traffic and addresses, as section 5.5 says for any node. Opaque names hide names, not behavior.
- A seized node gives its holder that node's own config and secrets, and lets them report false usage within the growth cap. That can cut a user everywhere until an admin stops counting the node.
- Changes made while a link is down (a disabled user, a removed device) reach the node only when the link is back, so the node keeps serving the old users until then.
- A user may pass the quota by what they move in the seconds between a poll and the sync that cuts them on the nodes that are up, and by a full quota on a node that cannot be reached.
- When a link is blocked, its node cannot be managed. It keeps serving and its operator can still reach the host directly.
- Management shares the fate of the link: whoever can stop the link's packets stops management. The link's transport is as visible as the node-links page says.
- A managed node's operator has agreed that node 1 can change anything on it. A wrong push is bounded by the trial and rollback, not prevented.

**Residual risks:**

1. The in-link TCP server on the remote is a new parser of packets from a link peer (G66).
2. Clocks. The panel and the nodes must agree on UTC days within about a minute, since the period boundaries decide when a cut lifts.
3. One managing panel per node and no chains. A node cannot be managed through two links, so one blocked link loses management of that node.

**Testing:** designed, not written. Planned: pairing vectors with `manage` (a changed value changes both fingerprints, old codes still read) and seeds for the existing `pairing` fuzz target, config tests for each validation rule, `tests/manage.rs` in core (two engines in one process, remote-dials and node-1-dials over `udp-obfs` and `tls`: a round trip, a 4 MiB transfer next to a user flow, a SYN from the remote refused, a link without `by_peer` resetting, a user sending to a link address refused, a link of a second operator never served), API tests for the relay route, both allowlists and both guards, panel tests of the usage merge, the cut and the derivations, and the two-node Docker gate `scripts/gate-nodes.sh`. Not reviewed by anyone outside the project.

### 5.20 WireGuard outbounds

A node may carry an exit through a WireGuard server of another party (`outbounds` of type `wireguard`, behind a `netstack` exit). The node is a WireGuard client of it: one task for each outbound owns a UDP socket connected to the server, a boringtun tunnel and its timers (`engine/wg_out.rs`), and a smoltcp stack on the outbound's own addresses (`engine/wg_stack.rs`) re-dials every flow of the exit from there. So the exit, the gate, the rules, the quotas and the counters are the ones every flow meets, and this section is about the one new edge: the server, which sees every flow, and whose packets are bytes this node did not write.

**Assets:** AS3 and AS4 (what the exit carries), AS5 (the outbound's private and preshared keys and its server address: the operator's secrets and an account with another party), AS2 (the node's address as the server sees it), and the node host with its networks.

**Capabilities:** the server sees the node's address, every destination name and address of the flows routed to it, and every byte the destination's own protocol leaves unprotected, as for any exit (5.15, "Not defended"). It does not see users, their tunnel addresses or keys: the node's own address in the tunnel is the one source of every flow. It can send any packet to the node inside the tunnel, with any source, to any address and port, at any rate, or none, and it can drop everything. Someone on the path between the node and the server can see the outer UDP, which is plain WireGuard (a fixed header, 32 bytes of overhead, no obfuscation), and block it. Someone who can answer the server's name differently can send the node to another endpoint.

| Risk | Design response | Mechanism | Status |
|---|---|---|---|
| **W1** The server is hostile and sees every flow, or answers with forged data | Nothing is hidden from it that the exit's destination does not hide: this is what the operator chose when the exit was given to that server, and the config doc and the panel say so. What the node adds is that the server cannot learn which user or device a flow belongs to (one tunnel address for all, a stack of the node's own, no user or device names in anything sent), and cannot reach the node beyond the tunnel: the stack answers only flows it opened, and the tunnel address is the one address it holds. DNS for users goes through the node's resolver and the outbound, so answers are as honest as the server and the node leaks no name outside it | `wg_stack`, `flows::lookup` | Built. The exposure itself is not defended, see below |
| **W2** The server sends packets the node did not ask for (a SYN to a port, an echo request, a datagram to a port no flow opened, a fragment, an extension header, a packet for another address) and learns from the answer | One gate in front of the interface: `wg_stack::admit` lets a packet in only when it is a whole TCP segment or UDP datagram for one of the outbound's own addresses (no fragment, no extension header, no ICMP, no other protocol), and the stack then checks that its source address, source port and destination port are those of a flow it has open. Everything else is dropped before smoltcp sees it and counted (`unsolicited`), so there is no RST, no ICMP error, no echo reply and no port that answers. The stack never listens. A UDP flow takes datagrams from its one destination only, from the port it was made for | `admit`, `Counters`, `run` in `wg_stack` | Built. Tests: the unit tests of `wg_stack` (every kind of unasked packet, random damage to real packets, flows that end), `what_the_server_sends_unasked_is_dropped_and_never_answered` in `tests/wireguard_outbound.rs` (a test-owned server sends nine kinds of unasked packet and gets nothing back), fuzz target `wg_stack` |
| **W3** The server floods the node or makes its memory grow | The queues between the socket task and the stack are bounded (1,024 packets each way) and a full one drops and counts. A flow's UDP socket holds 16 datagrams of 2,048 bytes on each side and its queue to the flow's task is bounded; TCP sockets have fixed buffers (256 KiB in, 64 KiB out) and the pipe to the flow's task is 32 KiB, so a slow destination holds the server back through the window and a slow reader of the exit holds the node's memory at those buffers. `max_flows` (16 to 16,384, default 1,024) caps the flows of the stack, TCP and UDP together, and a flow past it is refused with a reason and counted. The task has no unbounded buffer of the server's making. The stack's work is one task for each outbound, so a flood costs one core at most and slows that outbound's flows only | `QUEUE`, `RECEIVE`, `SEND`, `max_flows` in `wg_stack` | Built. Tests: `max_flows_refuses_the_next_flow_and_a_closed_one_frees_a_place`, the burst test of `wg_stack`. The buffers are zeroed memory that the system gives out as it is touched, so the cap at `max_flows` of 16,384 is a ceiling of several gigabytes that is reached only by that many busy flows |
| **W4** A forged answer for the server's name sends the node to another endpoint | A name is looked up by the system's resolver, outside every exit, at start, every 5 minutes and before each forced handshake. An address that is loopback, in an inbound's pool or the node's own is refused (`upstream::forbidden`), so a name cannot aim the node at itself or its networks. Private addresses are allowed, since a server on the operator's own network is a use of this outbound. A forged address can only be an endpoint that cannot complete the handshake, because the server's public key is in the config and the handshake is authenticated both ways: the outbound is then down and says so, and nothing is sent to it but handshakes. The last address stays while the name still resolves, so a lookup that fails or flaps costs nothing. This affects availability only | `resolve` in `wg_out` | Built. Tests: `a_server_that_resolves_to_an_address_the_node_never_dials_is_refused_and_down`, the config tests |
| **W5** A key leaks from the node | `private_key` and `preshared_key` are `Secret`s: shown as the marker by the control API and in every diagnostic, never logged (the reason an outbound is down names no key, and the server's address only as the operator wrote it), and taken back for the running outbound only with the same tag, server and public key, so a marker never gives the key to another server. A key that is written out in a document counts the outbound as changed. Validation refuses a private key that is the server's, that is any inbound, device or link key of the config, or that another WireGuard outbound uses, so that a leak of one key opens nothing else and no two outbounds look alike to a server. The tunnel keeps the keys in memory like every other tunnel of the node | `Secret`, `Config::parse_keeping`, `validate`, `Config::redacted` | Built. Tests: `config_wireguard_outbound.rs` (markers, the nodes' own keys, shared keys) |
| **W6** A flow leaves around a down tunnel | An outbound is down when an initiation has gone unanswered for 20 seconds or a datagram could not be sent, and then every flow of the exit fails at once with the reason (`out.connect` and `out.udp` look at the health first). No arm of the code falls back to a direct socket: `unsupported.udp` must be `reject` or `drop` (validation refuses `direct` and `via`), a lookup of the node's resolver through the exit is not asked of any other way, and the exit counts as not working (`Plan::working`, the exit's state and `ExitWorkingChanged`) from the moment the outbound is down, so devices without a choice of exit leave through `routing.fallback` when the operator named one (validation warns that this changes where their traffic leaves). A down outbound sends a new initiation after 2 seconds, then 4, doubling to 60, forever, and every change is logged at info with the reason | `WgOut::connect`, `WgOut::udp`, `watch`, `Plan::working` | Built. Tests: `a_server_that_stops_makes_the_exit_down_and_one_that_returns_makes_it_work_again` (nothing left around, back without a restart, the event once each way), `an_exit_through_one_has_no_way_around_it_...` |
| **W7** The path to the server blocks WireGuard | The outer UDP is plain WireGuard and a censor can recognize and drop it, which this outbound does not hide: it is for servers the operator reaches over a path that carries WireGuard (a server in the same network, or at a provider that is not blocked). When the path blocks it the outbound is down and says why (`the server did not answer a handshake for 20s`), and the exit does not work until the path does. It never falls back to a TCP or direct path | `wg_out::run` | Not defended: the outer UDP is not obfuscated. Use an `xray` outbound where WireGuard is blocked |

**Not defended:**

- The server sees what the exit sees. There is no anonymity from it, and it can correlate every flow of every user routed to it. DNS answers and unprotected content from it can be forged.
- The outer UDP is recognizable as WireGuard.
- A WireGuard server may hand out the same address to a node that crashed and came back, or keep sessions after the key is replaced: that is the server's own business, and what a stale session costs is a handshake.
- One task and one smoltcp stack carry all flows of an outbound, so an outbound cannot use more than one core, and each flow is terminated twice: once for the user's connection and once in the stack (G68).

**Residual risks:**

1. boringtun and smoltcp parse the server's bytes. A bug in either is a bug in code this project does not own. `admit` keeps what smoltcp sees to whole TCP and UDP packets of live flows, which keeps most of smoltcp's input surface (ICMP, fragments, options of unknown flows) away, but a flaw in smoltcp's TCP state machine on a flow the server was let to answer is reachable by the server. The stack runs inside the node process with the node's privileges and the node's keys.
2. The pools and the node's own addresses are held against the endpoint when it is looked up and when a name changes. An address of the host that is added after the lookup is not seen until the next lookup, 5 minutes at most.
3. A server that answers the handshake and then drops all data keeps the outbound up, since up is read off the handshake: flows through it stall and time out, and the exit is not marked down until a rekey or a keepalive without an answer makes the handshake unanswered, which is within about 2.5 minutes on an idle tunnel and within about 35 seconds on one that carries traffic.
4. `bind` and `interface` tie the outer socket as for a `direct` outbound. A host with other tunnels sends the outer UDP by its routing table where neither is set.

**Testing:** `crates/veilway-core/tests/config_wireguard_outbound.rs` (the document: validation, keys, markers, `via`, the exit's rules), `tests/wireguard_outbound.rs` (two nodes in one test, where a node's `wireguard` inbound is the server: TCP, UDP and DNS through the outbound, a proxy inbound on it, the server stopped and started, `max_flows`, an address family the outbound lacks, a name that resolves to a refused address, throughput, a test-owned hostile server), the unit tests of `engine/wg_stack.rs`, and the `wg_stack` fuzz target. Not yet reviewed by anyone outside the project.

## 7. Security invariants

Code review holds every change to these. Each has a test or measurement that decides it. "Planned" means the code it constrains does not exist yet; the invariant applies from the first commit of that code.

**Wire and probing**

1. A listener sends no byte to a peer that has not authenticated, except bytes the decoy itself would send (stream transports) or nothing (datagram transports). The spec lists the exceptions. The exception of `tls` below does not apply to `faketls` (designed, not built): its node writes no byte of its own to a stranger and relays the borrowed site's bytes, and the only bytes it composes for a peer that is not a user are the flight made for a hello whose carrier opened (which only a holder of the profile or a copy of a user's hello can cause) and a close when the site is down or a budget or cap is reached. Planned with the native transports: on `tls` the node ends TLS itself, so the TLS handshake a peer meets is the node's own and not the decoy's, which is why `tls` is capped at Detectable in version 1 (invariant 7a); while the decoy origin cannot be reached a stream listener closes the peer's connection with no answer, and the node can be identified for as long as that lasts; on `udp-obfs` an interferer on the path that holds back a real opening packet and sends it first from its own address gets the node's first answer, a packet of random bytes no larger than the one it sent, and only when the packet it took carries a handshake initiation that the node's WireGuard has not seen. Built, on plain `udp`: above the inbound's handshake load limit the node sends a cookie reply to anyone who can compute the first check, which needs only the inbound's public key (Q14), and after a restart a replayed handshake initiation is answered (G18). Test: probe differential and UDP silence test, section 5.1. Planned; violated today by `ws` (G1).
2. A client proof accepted once is not accepted again, including across a restart of the node: WireGuard initiations, `udp-obfs` opening packets, the stream proof of `tls`, `ws` and `fronted`, `faketls` proofs. On the obfuscated transports the mechanism is a time window around the node's clock, a cache of accepted proofs, a floor below which nothing is accepted, and a limit that is written to disk before any timestamp above it is accepted. The floor, the limit and, on a clean stop, the cache are kept in a replay file of their own, separate from the usage state file, and a node that cannot write that file accepts no proof. Two operator actions reopen replay, and each is documented with that cost: restoring a replay file from a copy, and `veilway replay reset`. Test: replay of captured valid handshakes, before and after a restart, gets the decoy or silence. Built on the node for `udp-obfs`: `an_opening_packet_is_accepted_once_across_a_clean_stop_and_across_a_kill`, `a_node_without_a_usable_replay_file_refuses_every_proof_for_the_window`, `a_node_that_cannot_write_its_replay_file_opens_no_new_session_and_says_so`, `no_obfuscated_transport_runs_without_a_replay_file_the_node_holds_alone`, `a_floor_ahead_of_the_clock_is_said_loudly_and_a_reset_ends_it`, the tests of `engine/replay.rs` for the file, its lock, its writer and the reset, and the fuzz target `replay_file` for the rule. A third thing reopens replay next to the two operator actions, and the node cannot prevent it: a lost or unusable file on a node whose clock is behind where it has been (G44). Planned for the stream transports. Partial for WireGuard: holds within one process lifetime only (G18).
3. On one node, the reject path and the path taken by a valid TLS client with no proof are indistinguishable in bytes and timing, and proof comparison is constant time. The version an update installs is taken from signed data (a signed manifest, or the version read from the verified artifact and compared before install), and is strictly greater than the running one. Test: updater test with a higher version in the metadata and an older signed artifact. Not built (G16).

The only connections not caused by user traffic are the ones in a documented list: update check, subscription refresh, geo data refresh, add-on install, ACME, outbound health checks, and the lookup of an exit's public address and country. Each can be switched off, and each fetch obeys invariant 27b. A subscription refresh happens only inside a tunnel of the subscription's own profiles or on the user's request, and can be switched off per subscription. Test: a run in an isolated network namespace with every destination logged and compared with the list. Planned.

Built as practice (two uses: the Wintun library load in `veilway-client`, the `TUNSETIFF` call of the `l3` exit in `veilway-core`), enforcement planned.
37. Release builds use committed lockfiles. CI references actions by commit hash and tools by exact version. Signing secrets are exposed only to the signing step. Test: workflow lint in CI. Partial (G8).

**Proxy inbounds**

38. A proxy inbound (`socks5`, `http`, `mixed`) carries nothing for a connection that has not logged in as a user with a `proxy_password` that the inbound admits, and offers no anonymous method. What it carries is a flow of that user, decided by the gate, the rules, the user's exits and quota exactly as the tunnel's are (the one `xray::connect`, and `xray_udp::associate` for UDP). The relay of UDP ASSOCIATE is on the node's own address and carries only datagrams from the IP address of the control connection. A listen address that strangers reach needs `public`, and then validation warns. The connections of a user end within a second of the user being cut off, of the password changing, or of the inbound no longer admitting them. Test: the tests of section 5.16, `a_reload_ends_the_connections_it_leaves_without_a_login`, fuzz target `proxy_front`. Built.

**Xray outbounds**

39. An exit whose Xray outbound is not carried by Xray does not carry: its flows end with a reason, and none goes to `direct`, to another exit or to the provider's default. An Xray outbound's server is dialed at an address the node looked up and the dial rules allowed, Xray's inbound for it is a Unix socket that only Xray's user holds, spoken to with a password made for each start, and the outbound's secrets and its link are never shown, logged or written back. Test: the tests of section 5.17. Built.

**Several nodes**

40. A node's control API is reachable only through its unix socket and through management connections of its one `by_peer` link, which run only allowlisted routes. Node 1 never accepts a management connection.

41. No user is sent to a node before its link's fingerprints were confirmed, and a node's per-user secrets are not valid on any other node.

**Speed limits**

42. A user's `speed_up` and `speed_down` only drop or delay: a limit never reroutes a flow, never moves it to another exit and never changes what a rule decided. TCP that the node holds as a stream (a `netstack` exit, the proxy inbounds, the Xray hop) is delayed, so nothing of it is lost; whatever the node only sees as packets (UDP, `l3`, `chain` and upstream exits, pings) is dropped over the rate and counted as `rate_limited`, in the user's `limited` counters. DNS, the control channel and what the node answers itself are charged to the bucket and are never dropped by it, so a user at the limit can still resolve names and keep the control channel up. The bucket is one atomic per user and direction, shared by all of the user's devices and doors, so more devices or connections get no more than the rate. A packet dropped for the rate on its way in still counts against the quota (it was spent before the check), and one dropped on its way out never counts. Node links and link accounts have no limit of their own: what a link carries is limited on the entry node, where the user is. Test: `crates/veilway-core/tests/speed.rs` (`tcp_download_through_a_netstack_exit_is_paced_to_the_rate`, `two_devices_of_a_user_share_one_limit`, `a_udp_flood_up_is_dropped_and_counted_and_still_counts_against_the_quota`, `dns_and_the_control_channel_are_never_dropped_while_the_user_is_at_the_limit`), unit tests in `engine/rate.rs`. Built.

**WireGuard outbounds**

43. An exit whose WireGuard outbound is down does not carry: its flows end with a reason, and none goes to `direct`, to another exit or to the server's default, and a UDP flow is never sent around the tunnel (`unsupported.udp` is `reject` or `drop`). The stack of an outbound answers nothing it did not ask for: a packet from the server that is not a whole TCP segment or UDP datagram of a flow the stack has open, from that flow's address and port, is dropped and counted and is never given an RST, an ICMP message or an echo reply. The outbound's keys are never shown, logged or taken back for another server, and a key is never one the config has elsewhere. Test: the tests of section 5.20. Built.

## 9. Non-goals

Stated so that nobody assumes otherwise. Docs and UI must not imply any of these are provided.

1. **Global passive adversary.** An observer who sees both the client's link and the node's egress can correlate flows by timing and volume. Veilway adds no mixing, batching or cover traffic and does not attempt to defeat this.
2. **Endpoint compromise.** Malware or an attacker with code execution on the client device, the node host or the panel host is out of scope. Keys in memory, the plaintext of traffic and the admin's session are all exposed. The measures in sections 5.4 and 5.5 limit how far one compromise spreads; they do not protect the compromised machine.
3. **Anonymity from the provider.** The node terminates the tunnel. The provider sees the client's address, the user's key, every destination, every DNS name, volume and timing, and the plaintext of anything not encrypted end to end. Veilway is a VPN, not an anonymity network. Chaining exits moves this trust to another operator without removing it.
4. **Unlinkability of a user across sessions.** The user's WireGuard key is the identity, and a node recognizes it on every handshake.
5. **Performance of IP over TCP.** `tls`, `ws`, `faketls` and `fronted` carry IP packets inside a TCP stream. One lost segment stalls every inner flow behind it, and inner TCP retransmits on top of outer TCP. This cannot be designed away. The mitigations (a datagram transport where the profile and the user put one first, automatic fallback, a few parallel connections, no second retransmission layer) reduce it. It is also a behavioral signature a censor can look for. Measurements are published per transport; no throughput claim is made without one.
6. **Durability of fronting and fake TLS.** Domain fronting works only on CDNs that still permit an SNI and `Host` mismatch, and that list shrinks. A `faketls` setup depends on the borrowed site keeping its TLS behavior and on the client's fingerprint matching a current browser, which changes with every browser release. Both are correct on the day they are measured and can stop working without any change in Veilway. They are shipped as lists the client probes and as fingerprints that can be updated, labeled "experimental, not externally reviewed" until someone outside the project has reviewed them.
7. **Proof of undetectability.** No obfuscated transport is claimed to be undetectable. The claim available is: these specific probes and these specific classifiers, on this date, did not distinguish it.
8. **Abuse prevention.** Veilway does not inspect user traffic to stop misuse of an exit. Rate and flow limits protect the node, not third parties.
9. **Protection of legacy protocols.** VLESS, VMess, Trojan and Shadowsocks run in an unmodified third-party sidecar. Their security is whatever that software provides. Veilway rates the profile and verifies the binary's hash, and nothing more.
10. **Denial of service by a well-resourced attacker.** Caps and timeouts stop cheap exhaustion. A volumetric attack on a node's address is out of scope.
11. **Physical access and coercion.** A seized, unlocked device exposes profiles and keys.
12. **Isolation that survives the operator's config.** Whether users reach each other, and whether they reach private networks behind an exit, is a routing decision that the config makes. The node enforces only what section 5.6 lists as holding whatever the rules say, and warns about the rest.
13. **A router's firewall for the node host.** An `l3` exit with `masquerade` makes the host forward. The node keeps tunnel traffic away from the host itself and delivers return traffic only for live flows. It does not firewall the host's other interfaces against each other.
14. **Confidentiality on a proxy inbound.** SOCKS5 and HTTP carry the password and the traffic in the clear. A proxy inbound is for loopback and private addresses, behind a tunnel or a TLS front the operator runs, and a public address is the operator's explicit choice with a warning. Docs and UI must not describe it as protected.

## 10. Open questions for the protocol spec

The spec for transports and the control channel must answer these before implementation. Each answer goes into the spec and, where it creates a rule, into section 7. The spec is the draft protocol pages in `veilway-docs` (Protocol overview, Transports, Control channel, Subscription format). "Answered by the spec" below means the draft takes a position. Nothing in it is built, measured or reviewed from outside, and every such answer is Planned.

- **Q1. Decoy fidelity.** Is the decoy a reverse proxy to a real origin or a TCP splice to it? A reverse proxy terminates TLS with the node's own stack and certificate, which is a fingerprint; a splice needs the decision made from the ClientHello alone. What happens to bytes already read when the decision is "not a client"? Answered by the spec, not built (Transports, "Accept state machine" and "`tls`"): neither as asked. A direct peer's request line is read byte by byte, and at the first byte that cannot belong to a candidate line, or at the end of a line whose proof fails, every byte read so far is written unchanged to a connection to the decoy origin that was opened before anything was read, and both directions are relayed. Behind the operator's web server the node forwards request by request through an existing HTTP/1.1 implementation. On `tls` the node ends TLS with its own stack, which is the fingerprint this question names, and `tls` is capped at Detectable for it.
- **Q2. Where the client proof lives per transport.** For `tls` and `ws` with an own certificate, is WireGuard's handshake the only proof, and if so what does a valid TLS client that never sends a valid WireGuard initiation see, and after how long? Invariant 1 has to hold during that wait. Answered by the spec, not built (Transports, "The stream proof" and "Accept state machine"): WireGuard's handshake is not the proof. `tls`, `ws` and `fronted` carry a proof of their own in the query part of the request target, and the node decides at the end of the request line (of the request head behind a trusted proxy), so a valid TLS client without a valid proof gets the decoy origin's answer with no wait beyond the hop to the origin. Still open: `faketls`, which is not specified.
- **Q3. Replay protection for `udp-obfs`, `faketls` and `fronted`.** Timestamp window, server-side replay cache, or both? What is the cache bound, and what does a node do after a restart, when the cache is empty? The same restart question applies to WireGuard's own timestamp memory (G18). Answered in part by the spec, not built (Transports, "The replay rule" and "The replay file"): both, for `udp-obfs`, `tls`, `ws` and `fronted`. A window of 60 s either side of the node's clock, a cache of accepted proofs (262,144 entries by default, and a full cache refuses every proof), a floor that follows accepted proofs, and a limit written to a replay file before it is used. After a clean stop the cache is read back, and after a crash the floor becomes the written limit. Still open: `faketls`, WireGuard's own timestamp memory on plain `udp` and the built `ws` (G18), and the spec's own question whether a clock fault should burn only the seconds that were used.
- **Q4. Transport secrets and retrospective detection.** If the `faketls` proof is keyed by a secret the node holds, a node compromise lets the attacker test recorded handshakes. Can the proof be keyed per user, or be made forward secure with a short-lived server key published through the subscription? How are these secrets rotated? Invariant 5b requires per-user secrets; which transports cannot meet it, and what does their profile say? Answered in part by the spec, not built (Protocol overview, "Keys and who holds them" and "Rotation"; Transports, "What a leaked key or a compromised node reveals"): the transport secret is per device, a device may hold two during a rotation, and the node transport key is rotated at least every 30 days and the retired one destroyed, because it still opens old tokens. On `tls`, `ws` and `fronted` the proof is sealed to the node transport key, so a device secret alone cannot be tested against recorded traffic, and it takes that key and the TLS plaintext to link one device's connections. `udp-obfs` is the transport that cannot meet invariant 5b in full, and it stays rated Detectable. Still open: `faketls`, where the spec lists this question as blocking.
- **Q5. Padding policy.** Target length distribution, who pays the overhead, and whether padding is negotiated on the control channel. How are the first exchange, the 120 s rekey pair and keepalives padded and jittered, and what is N in invariant 7? What measurement decides that a policy is good enough for invariant 7? Answered as a default by the spec, not built and not measured (Transports, "Padding", "Session activity and timers" and the tables of numbers): padding lengths are drawn uniformly from fixed ranges, the sender pays, and padding is never negotiated. A few ranges may be set in the signed profile and in the node's config. Wide padding goes on the first 16 chunks of each direction, on every chunk with a WireGuard handshake message and on every chunk with a control channel packet, the client starts the rekey 60 to 110 s after the last handshake, and an idle keepalive comes after 20 to 40 s of send silence. N in invariant 7 is 16. Still open: every range is unmeasured, the spec keeps them as an open question, and the length and timing measurement of section 5.1 decides.
- **Q6. Control channel authority.** Exactly which client settings a node may set (address, DNS, MTU, exit list, notices, hints) and the bounds on each. May a node push routes? May a transport hint point the client at an address that was not in the signed subscription, and how is that rated? What is the request credential and framing that keeps other software on the client device, web pages included, from using the channel (invariant 13a)? Answered for version 1 by the spec, not built (Control channel, "Who can use it", "The credential", "Addresses and resolver" and "What a malicious node can do"): the only value a client applies is a lower MTU, from 1280 to the signed profile's. Addresses and the resolver are reported and compared, never applied. The exit catalog, usage and notices are shown within fixed bounds. A node pushes no routes, and a hint is two indices into the signed profile's own lists, so it can name nothing that is not already there. The credential and framing are those of invariant 13a. Still open in the spec: whether a later version lets a node add an address family.
- **Q7. Inbound filtering on the client.** Should the client drop inner packets that do not belong to a flow it opened, so that a node cannot reach services listening on the tunnel interface? What does that cost applications that expect inbound connections?
- **Q8. DNS memory.** Per-peer keying (invariant 15), entry lifetime, bound per peer, and behavior when two names share an address. How are domain rules evaluated for a flow whose address was never resolved through the tunnel? Answered by the built engine, and to be written into the spec: the memory is per user (not per device), holds 4096 entries of one name with one address each, keeps an entry for the answer's TTL clamped to 60 to 3600 s, lets several names share an address, and a flow to an address the user never resolved through the node matches no `domain` condition.
- **Q9. Key custody.** Does the panel generate and store user private keys in order to render subscriptions, or does the client generate its key and register only the public half? Where does the provider's Ed25519 signing key live when panel and node share a host? How does a client learn of a legitimate signing key rotation? Answered in part by the spec, not built (Subscription format, "Device keys", "Keys held for a subscription" and its open questions): by default the device makes its key and enrolls only the public half, with a device secret, and a key made and kept by the panel is the stated weaker option, which a whole document in a link has to use. A client learns of a rotation from the list of signing keys in a document signed by a key it holds, during an overlap of two keys, and a client that missed the whole rotation needs a new link. A retired signing key is kept for 365 days to sign the refusal that says so, then destroyed. Still open: where the signing key lives is left to the provider. Enrollment needs a document signed for each device, which pushes providers towards signing online, and a stolen key cannot be revoked.
- **Q10. Geo data verification.** A pinned hash cannot cover a file that is refreshed on a schedule. Which signature scheme and whose key, for sources this project does not control?
- **Q11. First install.** How is the first download of a client or server binary verified where the release host is blocked or impersonated, and what does the one-line installer check?
- **Q12. Reproducible builds.** Are they a goal, so that a signed artifact can be checked against the source?
- **Q13. Parallel connections.** How are WireGuard datagrams spread across several stream connections without reordering beyond WireGuard's replay window, and does the set of parallel connections itself form a recognizable pattern? Answered in part by the spec, not built (Transports, "Stream transports and TCP inside TCP"): 1 connection by default and at most 4 where the profile allows, each its own session, and the connection for a datagram is picked by a hash of the inner packet's addresses, protocol and ports, so one inner flow stays on one connection and in order. A connection that stalls for long can still put packets outside WireGuard's replay window. The spec says that several long-lived connections are a pattern. Still open: whether more than 1 is worth that pattern, which is unmeasured.
- **Q14. Cookie replies.** Under load a WireGuard endpoint answers anyone who can compute `mac1`, which needs only the node's public key. Should obfuscated transports suppress cookie replies and rate-limit in the transport instead? Answered by the spec, not built (Transports, "WireGuard on an obfuscated transport", rule 5): yes. A node never sends a cookie reply on an obfuscated transport, handshake messages there do not pass the inbound's handshake load limiter, and load is limited per session, per device and per source in the transport. Plain `udp` keeps the cookie reply as a stated exception.
- **Q15. Subscription fetch.** The first fetch happens outside any tunnel, to a provider URL the censor may know. Does it use the same fronting options as the transports, and may later refreshes be forced through the tunnel? Answered in part by the spec, not built (Subscription format, "When a fetch happens" and "When nothing works"): later refreshes are automatic only through a tunnel of the subscription's own profiles. Every other fetch, the first included, leaves only after the user asked, from the device's own address or, when the user chooses it each time, through another subscription's tunnel. Still open: whether a fetch may use the fronting options, which the spec does not specify. Other refresh endpoints signed into the document, a signed move of the main endpoint that the user confirms once, static mirrors and a whole document carried in a link are its answers to a blocked host. The exchange is sealed end to end, so a plain `http` endpoint or a content delivery network in front of the endpoint learns no token.
- **Q16. Front probing.** Probing many front candidates in a burst is itself a behavior. What pacing and order does the client use, and does a failed probe leak the profile's SNI list to the path? Answered by the spec, not built (Transports, "Choosing a candidate"): there is no probe request, and trying a candidate is opening a real session on it. The candidate that last worked on the network is tried first and alone, then the list in an order that is random per installation, at most 2 in flight 250 ms apart and at most 6 distinct candidates per hour per network. The spec states that what a client tries reveals part of its candidate list to the path.
- **Q17. `direct` and `via` policies.** When ICMP or other protocols leave from the node's own address, which destination gate applies, and how is invariant 12 expressed for an exit that is no longer proxy-only? Answered by the built engine: the gate is one list for every exit and is checked before any policy, the node's own addresses are a routing matter (`host:self`), `direct` and `via` are a validation error unless the exit says `"proxy_only": false`, and a `via` target must be in the user's `exits`. Still open: how a client is told that an exit is not proxy-only, which belongs to the rating (Q21).
- **Q18. Source-country filtering on inbounds.** Refusing clients by source country happens before authentication. What does a refused client see, given invariant 1?
- **Q19. `faketls` fidelity.** How does the authenticated `faketls` server flight match the borrowed site's record lengths, and how is the borrowed site chosen so the node's ASN is plausible for it? What caps apply to unauthenticated splices so that the node is not an open forwarder?
- **Q20. `udp-obfs`.** Key source, header randomization, junk packet schedule and replay rule. What does a prober holding the node public key but no user secret see, and what does a holder of another user's subscription see? Answered by the spec, not built (Transports, "`udp-obfs`" and "Keys derived from the device transport secret"): the keys come from the device transport secret, the opening packet carries an epoch tag masked under a key derived from the inbound's public key, a fresh salt and a sealed timestamp, data packets use fresh random nonces, and the replay rule is the one of Q3. There are no junk packets, only padding and padding-only packets, and the spec says they may come back. A prober without a device secret gets silence, except an interferer that holds back a real opening packet and sends it first from its own address, which gets the node's first answer when that packet carries a handshake initiation the node's WireGuard has not seen. A holder of another device's subscription for the same inbound can link two opening packets of one device within an epoch of 120 s, and can neither name the device nor open the packets.
- **Q21. Rating definition.** `PLAN.md` rates "verified TLS or fake TLS around an encrypted protocol" as Protected. Under that wording the built `ws` transport rates Protected, while section 5.1 shows it is detectable by its ClientHello and by probing (G1), and the label reads as a claim that non-goal 7 rules out. The definition must be rewritten to match invariant 7a before Phase 2: a rating follows from recorded test results per release and from the weakest listener on the address, not from the transport's name. Answered by `PLAN.md` ("Security rating shown to users"), invariant 7a and the spec, not built (Obfuscation layer status, "How a profile is rated"): a rating above Detectable needs recorded tests for the release and an address with no weaker listener, the built `ws` is rated Detectable, and in version 1 no native profile is rated higher. Still open, for the owner: whether the top rating keeps the name "Protected", which the spec says invites the reading that non-goal 7 rules out.
- **Q22. Certificate pinning and CDNs.** Invariant 5a covers `tls` and own-certificate `ws`. What does a profile carry for CDN-terminated transports, where the certificate is the CDN's and rotates? Answered by the spec, not built (Subscription format, "Transports of a profile" and its open questions; Transports, "`ws`" and "Refusals and clocks"): none. Pins belong to a candidate, at most 4 each: every `tls` candidate must have them, a `ws` candidate may, and a `fronted` candidate has none. A candidate behind a CDN relies on ordinary validation, and the tunnel inside does not depend on it. The cost: such a client takes no clock offset from a `Date` header, so with a wrong clock it cannot connect to a profile whose only cover transports run through a CDN, and whoever can present a valid certificate for the front reads the token and the framing, as the CDN does.
- **Q23. Borrowed-site mode.** The Borrowed-site mode page answers Q19 and Q4 as a design and leaves these open, the first six being the ones to review first: whether the proof is sound; whether the node's flight can be made close enough to the site's, from its live answer to each hello and at most 32 samples where there is none, that a classifier trained on the site's real flights cannot tell them apart; whether a throwaway P-256 key derived from the shared secret, with a leaf signed by nothing, is sound and accepted by a TLS library as the client; how the client sets the key share, `random` and `legacy_session_id` after the rest of the hello is final, which BoringSSL does not support; whether the node's handshake should be a purpose-built writer; and whether a leaked transport key, which opens every recorded hello, can be limited by a short-lived key published in the subscription. Whether the project should ship it at all was decided for an alpha, off by default.

## 11. Keeping this document true

- A change that adds a parser adds its row to section 6 and its fuzz target in the same change.
- A change that builds a planned mechanism updates its status label and names the test that covers it. A status never moves to Built on the strength of code alone if the row names a test.
- A change that closes a gap in section 8 marks the row closed, keeps its id, and names the test in the relevant subsection of section 5. Ids are never reused or renumbered, because other documents refer to them. A gap closed in code without a test says "closed in code, not in a test".
- A change to the engine that moves a property from "always enforced" to "decided by the config", or back, updates the two lists at the top of section 5.6.
- A new transport, exit backend, file format or network-facing endpoint is not merged without an entry in sections 5, 6 and 7.
- Nothing in user-facing docs or UI describes a security property that this document marks as planned, partial or not defended.
